## Dependency notes

- **Story 17 (TM-21) is the entry point for this feature and the gate on four others.** It creates `tickets` and `requesters`, so **TM-22, TM-23, TM-45** and [`../categories-priorities-statuses/15-story-protect-referential-integrity-on-category-delete-TM-18.md`](../categories-priorities-statuses/15-story-protect-referential-integrity-on-category-delete-TM-18.md) are all hard-blocked on it. Confirm with `php artisan db:table tickets` before starting any of them.

- **Story 17 opens a data-integrity window that only TM-18 closes, so TM-18 must ship immediately after it, in the same sprint.** The four master-data foreign keys are `ON DELETE RESTRICT`, but a category soft delete is an `UPDATE` and never trips them — and a soft-deleted category still accepts new tickets, because the foreign key cannot see `deleted_at`. Both reproduced on `mysql:8.4` during Story 15's planning. Between TM-21 landing and TM-18 landing, an admin can orphan every ticket in a category with one click.

- **Story 17 is schema, models and one service. It touches no HTTP layer at all.** `backend/routes/api.php`, everything under `backend/app/Http/`, `backend/database/seeders/` and all of `frontend/` are left unchanged, and `RouteAuthorizationTest` is not edited. It cannot conflict with in-flight work in the other two feature folders.

- **`SELECT MAX(reference) … FOR UPDATE` does not satisfy criterion 3, and the failure is loud.** Measured on `mysql:8.4.11`: two concurrent sessions both read `none` for a fresh year, because **InnoDB gap locks do not conflict with one another** — a gap lock blocks inserts, not other gap locks. Both computed `TKT-2027-000001`, and the racing inserts produced **`ERROR 1213 (40001) Deadlock found`**, not a clean `1062`. `EXPLAIN` also shows that query is a full scan of the reference unique index, so it degrades with every ticket ever filed. **Story 17 forbids that implementation and forbids papering over it with a retry loop.**

- **What works instead: a one-row-per-year `ticket_sequences` table and a single atomic upsert.** `INSERT … VALUES (?, LAST_INSERT_ID(1)) ON DUPLICATE KEY UPDATE next_number = LAST_INSERT_ID(next_number + 1)`, then `SELECT LAST_INSERT_ID()`. Measured: with the row present the second session **blocked 2 s** and then received the next number; on the first-ticket-of-the-year race one session got `1` and the other `2` with **no deadlock** (a single unique key is what keeps that path clean — **do not add a second unique index to `ticket_sequences`**); and allocating inside a `DB::transaction` that then throws **returned the number**, leaving `next_number` unchanged. Gap-free and collision-free, with no read-modify-write window. `TicketReferenceGenerator::next()` throws `LogicException` outside a transaction, because that last property depends on it.

- **A `FULLTEXT` index is invisible inside an open transaction, and `RefreshDatabase` opens one.** Measured: after inserting a ticket inside `BEGIN`, `LIKE '%Kerberos%'` found it and `MATCH(subject, description) AGAINST('kerberos')` found **nothing**; after `COMMIT`, `MATCH` found it. InnoDB updates the index at commit time. So a `MATCH` test under `RefreshDatabase` fails with zero rows and no error. **Story 17's FULLTEXT test uses `Illuminate\Foundation\Testing\DatabaseTruncation`, and TM-25's entire search suite must do the same.** This is the single most likely way to lose a day in this feature.

- **Two hard limits TM-25 must design around, both measured.** `innodb_ft_min_token_size = 3`, so a search term shorter than three characters returns **nothing** from `MATCH` — confirmed with `on` and with the Arabic `لا`. And common English stopwords such as `the` are unsearchable: `the` is in `INNODB_FT_DEFAULT_STOPWORD`. This is *not* the MyISAM 50 % rule, which does not apply — a non-stopword present in every row matched every row. TM-25's `q` also covers `reference` and the requester's name and email, none of which are in this index, so those stay exact-match and `LIKE`.

- **Arabic needs no special parser.** Measured: `MATCH … AGAINST('الطابعة')` matched an Arabic subject and description with the default parser on utf8mb4. No `WITH PARSER ngram`, which would have been needed for CJK.

- **The escalation and lifecycle column names come from stories two sprints away.** Criterion 2 says "the escalation columns and the resolved/closed timestamps" without naming them; `backlog.json` does. `E6-S5` (TM-41) names `escalation_level`, `escalated_at`, `escalated_by` and `escalation_reason`; `E6-S3` (TM-39) names `resolved_at`, `closed_at` and `first_responded_at`.
