## Dependency notes

- **Story 28 is the only frontend-only story in this epic, and it is the most blocked.** It adds no backend file at all — every figure and filter it needs comes from Story 20's `assigned_to=me` / `status_id[]` and Story 25's `mine_open`. In exchange it is hard-blocked on **three** unimplemented stories (19, 20 and 25) and cannot start until all of them land.

- **Story 28 satisfies AC2 by reusing the view itself, not by extracting a table component.** Story 19 puts the ticket table inline in `TicketListView.vue`, so `/my-tickets` is registered against **that same component** with `meta: { scope: 'mine' }`. No `MyTicketsView.vue`, no `TicketTable.vue`, and every `data-testid` Story 19 defined stays put so Stories 19, 20 and 25's specs keep passing. **If a third consumer of the table ever appears, that is the story that earns the extraction — not this one.**

- **A measured trap Story 28 is built around: navigating `/tickets` → `/my-tickets` does not remount the shared component.** Measured against the project's own `vue-router 4.6.4` — the transition fires watchers only, with no `onMounted` and no `onUnmounted`, while leaving to a different component and returning *does* remount. So the route preset must be wired to **both** `onMounted` and a `route.fullPath` watcher, with an idempotent handler. An `onMounted`-only implementation silently ships resolved and closed tickets on the most common navigation path.

- **"Open" means `statuses.is_terminal = false` everywhere in this epic, never `bucket = 'open'`.** `bucket` has three values and a `pending` ticket is still on someone's plate. Story 25's `mine_open` uses `is_terminal`, and Story 28's route preset and nav badge must agree with it or the badge will contradict the row count on screen. Story 28 adds `openStatusIds` / `terminalStatusIds` to the master-data store as the authority; Story 25's `DashboardView` keeps its own derivation off `stats.by_status` **deliberately**, to avoid a blocking await on first paint.

- **AC4 of Story 28 says "sidebar"; this app has a header nav and no sidebar.** The count is rendered as a badge on the `nav-my-tickets` link, shown only when it is greater than zero — which also means an admin normally sees nothing while a **demoted agent still holding tickets** sees their real number. The substitution is recorded rather than resolved by inventing a sidebar.

- **The `mine_open` badge is refreshed on assignment events, never polled — and TM-38 owes it the third call.** Story 28 adds `stats.load()` after Story 26's `assign()` and Story 27's `claim()`. A status change into `resolved` or `closed` moves the same figure, so **TM-38 must add the same call** or the badge goes stale until the next sign-in. Nothing in this epic should replace that with a timer.

- **Story 29 splits AC3 across two sprints, and that split is deliberate.** TM-34's third criterion asks for a notification, but **E8 (sprint 5) owns every line of mail**: TM-51 the queue and Mailpit guarantees, TM-52 *"Notify an agent when a ticket is assigned"*, and TM-57 the rule that *"no notification is sent inline during a request"*. So Story 29 delivers the **rule and the dispatch point** — `App\Events\TicketAssigned`, dispatched once per real assignment, **outside** the transaction — and leaves the listener and mailable to TM-52. A synchronous send here would be deleted by TM-57; building the queue here would swallow TM-51 whole. **Verification step 8 of Story 29 checks Mailpit is empty**, which is how that boundary is enforced rather than merely stated.

- **"Does not notify the previous one twice" is implemented as "zero times".** TM-52's fourth criterion says *"Unassigning sends no email to anyone"*, so the reading consistent with both stories is that only the **new** assignee is ever notified. `TicketAssigned` therefore does not carry the previous assignee and unassign dispatches nothing — there is no dedup bookkeeping to get wrong. Consequence recorded rather than hidden: **an agent whose ticket is taken away learns about it in the app, not by email.** A courtesy notice is a TM-52 conversation; **do not add a `TicketUnassigned` event speculatively.**

- **Story 27's claim endpoint must never dispatch `TicketAssigned`.** TM-52's third criterion is *"No email is sent when a user assigns a ticket to themselves"*, and a self-claim is exactly that. Story 29 records this so TM-52 does not have to infer it. Relatedly, `assignee === actor` is currently **unreachable** on `/assign` (TM-31 requires an active **agent** target and only admins may call it), so no self-assign guard is written — if that rule is relaxed, TM-52's criterion is where the guard belongs.

- **AC2's "shown in the timeline" is a forward constraint on TM-46 (sprint 4), like Story 24's statistics clause was on TM-29.** Story 29 ships the storage contract — `meta.reason` on the activity row, absent rather than null when no reason was given — and documents the exact key so TM-46 renders it without guessing. It deliberately does **not** surface the reason on the ticket detail page, which shows current state and would become a second, competing source of history. **TM-46 and TM-64 own escaping it**: the reason is stored verbatim, because sanitising on the way in would corrupt a legitimate reason containing `<`.

- **A measured footgun the whole epic inherits: `assigned_to: ""` unassigns, and no server-side rule can prevent it.** Laravel's `ConvertEmptyStringsToNull` rewrites `""` to `null` **before** validation, so the API cannot distinguish an empty form field from a deliberate null — measured through a real HTTP request. The mitigation is the typed client (`number | null`, never `''`) plus documentation plus a test that pins the behaviour as intentional. **Do not "fix" it by removing the middleware** — `reason: ""` relies on the same rewrite to become a null reason rather than an empty-string one.

- **Story 29 creates `backend/app/Events/`, the project's first.** It holds one event with scalar ids and no marker interfaces — no `ShouldQueue`, no `ShouldBroadcast`, no `SerializesModels` — because adding them now would change the event's behaviour the moment TM-51 starts a worker. Ids rather than models because TM-52's listener will be queued and would re-fetch anyway.

- **Story 27 does NOT relax `TicketPolicy::assign()`, and that supersedes what Stories 22 and 26 both anticipated.** Story 22's docblock on `assign()` and Story 26's plan each say TM-32 would relax it so an agent could claim an unassigned ticket. It cannot: a precondition encoded in a policy can only ever produce `403 This action is unauthorized.` (the exact string `RouteAuthorizationTest.php:40` asserts), and TM-32's third criterion requires a **`409` naming the current holder**. So Story 27 adds a separate `claim` ability and a separate `POST /tickets/{ticket}/claim`, and `assign()` stays `$user->isAdmin()` for TM-34 to extend with unassign. **Two verbs, two audiences, two idempotency rules** — an admin's reassign is last-write-wins, an agent's claim is first-write-wins. Do not merge them later.

- **Story 27 splits one affordance across two layers on purpose.** `TicketPolicy::claim()` is a pure role gate (`! $user->isAdmin()`) so a contested claim reaches the handler and gets its `409`; the *"is there anything to claim"* half lives in `TicketResource`'s `can.claim` as `… && $this->assigned_to === null`. Moving that state check into the policy turns AC3's conflict into a `403` — Story 27's `test_contested_claim_is_a_conflict_not_a_forbidden` exists to catch exactly that, and its verification step 5 asks you to prove it.

- **AC1 of Story 27 is already owned by Stories 19, 20 and 25, and Story 27 rebuilds none of it.** Story 25's `stat-unassigned` card links to `{ name: 'tickets', query: { assignee: 'unassigned' } }` — its plan says the card is kept queue-wide *"because E5-S2 (self-claim) is built on exactly this"* — and Story 20 supplies the `unassigned` sentinel and the `filter-assignee` select. Story 27's only AC1 obligation is one round-trip regression test. **If the team resequences and any of the three is missing, AC1 is deferred and recorded, never faked with a second entry point.**

- **`agent-policy` is a new route-authorization level, introduced by Story 27.** `tickets.claim` is the project's first route an **agent** may reach and an **admin** may not, so `RouteAuthorizationTest` gains a fifth level plus `test_admin_refused_by_agent_policy_routes`. Like the `admin-policy` tests before it, that test needs a **real** ticket id — binding resolves before the policy, so id `999999` returns `404`, not `403`.

- **A trap this epic lays for the notification stories (TM-42 onward): the claim is written with a conditional `UPDATE`, which fires no Eloquent model events.** Measured — `Ticket::query()->…->update(…)` fired **0** `updated` events where `$model->save()` fired one. Story 26's assign uses `save()` and would be visible to an observer; Story 27's claim would not. **Detect assignment changes from `ticket_activities`, not from a model observer.**

- **Story 26 is gated on Story 22 (TM-26), not on the rest of the ticket feature.** TM-26 supplies `TicketPolicy::assign()`, the show-route `can` block, `TicketDetail` / `loadTicket()` on the SPA side, and `TicketActionToolbar.vue`'s disabled Assign button — which Story 26 exists to enable. As of 2026-08-26 TM-26's backend half is in the working tree and its test file is not written yet. **Gate: `php artisan test --filter='TicketShowTest|RouteAuthorizationTest'` green.**

- **Story 26 may have to create `TicketFactory` and `RequesterFactory`, which Story 19 (TM-23) owns.** `backend/database/factories/` currently holds only `UserFactory.php`, and `backend/tests/Feature/Tickets/` does not exist. Story 26's task 8 creates both **verbatim from Story 19's task 6** when they are still absent, and records it in the PR description so Story 19 does not add a second variant. If TM-23 ships first, that task is skipped.

- **Story 26 closes a question Story 20 (TM-24) deliberately left open, and the answer is "neither".** TM-24's task 11 handed TM-31 the choice of introducing `GET /api/v1/staff` or relaxing `UserPolicy::viewAny()`. Story 26 does **neither**: every staff-list consumer that E5 actually specifies is an admin (assign, TM-34's reassign, TM-35's workload), and TM-32's self-claim needs no colleague list at all — so it adds a single `role` filter to the existing `GET /api/v1/admin/users` instead. **Consequence: TM-24's agent-facing assignee dropdown keeps offering only Anyone / Me / Unassigned.** The first story that gives an *agent* a named-colleague picker is the one that must re-open `/staff`.

- **`TicketPolicy::assign()` stays admin-only through Story 26 — and, as the first note above records, through Story 27 as well.** Story 26 still registers `tickets.assign` as `admin-policy` — policy-gated, with **no** `admin` middleware — rather than nesting it in the admin route group, because **TM-34** extends that endpoint with unassign and should not have to move it. `RouteAuthorizationTest::test_policy_admin_routes_have_no_admin_middleware` enforces the distinction automatically.

- **Story 26 stops at "assign to a named active agent", and three of its five neighbours own the obvious next steps.** `assigned_to: null` is a `422` there because **TM-34** owns unassigning; the `reason` field is explicitly `prohibited` with a message naming TM-34; no notification is sent because TM-34's third criterion owns that; and no workload counts are computed because **TM-35** owns them. `AdminUser.tickets_count` already exists as an optional field in `frontend/src/api/users.ts` that no endpoint fills — that is TM-35's, and Story 26 leaves it alone.

- **A shared trap across this epic: an existing assignment survives its owner's deactivation.** Measured on `mysql:8.4` (`tm-mysql-test`, 3307) during Story 26's planning — `tickets.assigned_to` is `ON DELETE SET NULL`, and deactivation is not a delete. Validation rejects **new** assignments to an inactive user without retro-cleaning old ones, deliberately: **TM-35's fourth criterion exists to surface "inactive agents holding open tickets"**. No story in this epic should add a cleanup that would make that criterion untestable.

- **Every story here appends to `TicketActivityEvent` and none of them may rename a case.** `ticket_activities.event` is `varchar(50)`, so appending needs no migration — but the old strings are already in rows. Story 26 adds `Assigned = 'assigned'` and Story 27 adds `Claimed = 'claimed'`, and they share that file with Stories 23 (`Updated`) and 24 (`Deleted`) — four stories, four appends, one file. **Rebase before editing it.** `claimed` is deliberately a separate case from `assigned` rather than a flag on it: they are different sentences in TM-45's timeline, and the alternative encoding (*"`assigned` where `user_id === new_value`"*) breaks the first time an admin assigns a ticket to themselves.

- **Three files are contention points with the in-flight ticket-creation-tracking stories:** `backend/app/Http/Controllers/Api/V1/TicketController.php`, `backend/app/Enums/TicketActivityEvent.php` and `frontend/src/components/TicketActionToolbar.vue`. Stories 23, 24, 26 and 27 all add to the first two, and Stories 23, 26, 27, TM-38 and TM-41 each add or enable one button in the third — Story 27's `action-claim` is a fifth button, not one of Story 22's four placeholders. Place new methods after whatever is already present rather than at a fixed line.
