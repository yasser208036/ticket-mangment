# ticket-history-audit-trail — plan overview

Entry point for the **ticket-history-audit-trail** feature. Stories execute in order by their `NN` prefix. `NN` continues the global sequence that runs through [`../foundation-environment/00-overview.md`](../foundation-environment/00-overview.md), [`../authentication-agent/00-overview.md`](../authentication-agent/00-overview.md), [`../categories-priorities-statuses/00-overview.md`](../categories-priorities-statuses/00-overview.md), [`../ticket-creation-tracking/00-overview.md`](../ticket-creation-tracking/00-overview.md), [`../assignment-workload/00-overview.md`](../assignment-workload/00-overview.md) and [`../status-workflow-escalation/00-overview.md`](../status-workflow-escalation/00-overview.md).

Jira epic **E7 — Ticket History / Audit Trail**: *"An append-only record of every change to every ticket, surfaced as a readable timeline. This is the epic that makes the system auditable."* Five stories, TM-45 through TM-49, all sprint 4.

## Dependency notes

- **Most of TM-45's schema already exists, and none of it was tested.** `ticket_activities`, `TicketActivity`, `TicketActivityEvent` and `ActivityRecorder` were all written by TM-21/TM-22 as scaffolding for ticket creation. `grep -rln "ticket_activities\|TicketActivity\|ActivityRecorder" backend/tests/` returned **nothing** while planning — the audit trail meant to be *"complete by construction rather than by good intentions"* had **no test at all**. **Story 38 is a verification-and-enforcement story, not a build story**; its plan opens with a table marking each acceptance criterion done, unenforced, or not delivered.

- **AC3's `TicketService` clause is deliberately NOT delivered, and that deviation is raised rather than absorbed.** The story asks for `ActivityRecorder` to be called only from a `TicketService`. The single-**writer** rule is implemented and test-enforced; the service layer is not. Eight planned stories (26, 27, 29, 32, 34, 35, 37 and today's two controllers) call the recorder from a controller or a console command, so the clause would require an unscoped refactor **and would still be false** for the bulk `category_changed` path and Story 37's `tickets:flag-stale`. The clause names an implementation; the story's own "so that" names the outcome, and the outcome is one writer. **The PR must carry the deviation in writing and raise it with the backlog owner.**

- **Story 38 fixes a red test the suite has carried since TM-21.** `TicketReferenceTest::test_calling_outside_a_transaction_throws` fails because `RefreshDatabase` opens a transaction, so `DB::transactionLevel()` is `1` and the guard can never fire — **and the identical flaw makes `ActivityRecorder`'s guard, which is AC6's entire mechanism, untestable too.** Both services throw before touching the database, so the fix is a test class **without** the trait. Story 38 takes the suite from **3 failures to 2**.

- **Story 38 removes a landmine two other plans document in prose.** `ActivityRecorder::recordMany()` required all five attribute keys and stored the literal string `"null"` in the `json` `meta` column when one was omitted. Stories 26 and 37 each warn about it; **two plans documenting a footgun is the signal to remove it.** The defaults move into `recordMany()` and `record()` becomes a thin delegate. No caller breaks.

- **AC2 is enforced by the parameter type, not by scanning source for event strings.** A scanner would false-positive: Story 34 adds `TicketActivityEvent::Reopened = 'reopened'` **and** `Status::SLUG_REOPENED = 'reopened'`, the same string as a legitimate status slug. The real guarantee is that `record`/`recordMany` take `TicketActivityEvent` and not `string`, asserted by reflection.

- **AC3's first clause is a tripwire, not a proof.** A test scans `backend/app` for write idioms outside `ActivityRecorder` while **allowing reads** — Story 33's `TicketResource` and TM-46's timeline both read this table legitimately. **The structural guarantee is TM-48's**, which blocks updates and deletes on the model.

- **AC5's UI half is documented, not built.** There is no timeline; `GET /tickets/{ticket}/activities` and every component that renders an activity are **TM-46**. Story 38 delivers the data half and writes the contract where TM-46 will read it: `user_id` null means the system acted, and **no consumer may substitute a name for it**.

- **Story 38 owns two relations that Stories 33 and 34 each planned to add.** `TicketActivity::user()` (Story 33's task 5) and `Ticket::activities()` (Story 34's task 4) belong to the models this story owns. Whichever lands first adds them; **never twice**, and the PR records which.

- **`ticket_activities` was missing from `docs/erd.md` entirely** — no entity, no relationships, no table-notes row. Story 38 adds all three plus the null-actor rule.

- **Forward constraint on TM-47: an internal note must not touch `tickets.updated_at`.** Story 37 (TM-43) defines staleness as `tickets.updated_at`, citing TM-47's own criterion. If TM-47 lets a note bump that column, the stale command's definition silently changes.

- **Story 39 is the audit trail's first reader, and it is the story Story 38 was written for.** Story 38's closing line names it by number. Two of its deliverables are load-bearing: `Ticket::activities()` and `TicketActivity::user()` — whose docblock carries the rule that a null `user_id` means the system acted and **no consumer substitutes a name**. Story 39 is that consumer. **Verify both relations exist before starting Story 39**; if they do not, Story 38 has not landed and Story 39 must not add them itself (Stories 33 and 34 also claim them, and they must exist exactly once).

- **Story 39 renders eleven events by rendering none of them specifically.** Only `created` and `category_changed` exist in `TicketActivityEvent` today; nine more are planned across Stories 23, 24, 26, 27, 29, 32, 34, 35 and TM-47. Story 39 therefore ships **one event→icon/colour map with a real fallback** plus a sentence generator driven by the shape of the event value (`<noun>_changed` → *"changed \<noun\>"*), so `status_changed` renders as *"Ahmed changed status from Open to In Progress"* — the story's own example sentence — **the day Story 32 lands, with no edit to any timeline file.** A test pins that contract. **A later story that has to edit the timeline to add an event has broken it.**

- **Story 39 reads `meta` keys that five unimplemented plans promise.** `meta.from_name`/`to_name` (Stories 26, 32 and `CategoryController::reassignTickets()`), `meta.reason` — **omitted rather than null** when absent (Story 29), `meta.resolution` (Story 33), `meta.reference`/`subject` (Story 24), and the two competing category-change events Story 23 creates (`category_changed` vs `updated` with `field = 'category_id'`). Story 39's plan lists each with the plan file and line that promises it; **the API contract section it writes into `docs/api-contract.md` is where later stories should look before inventing a sixth key.**

- **Story 39 takes Story 32's baseline test failure, deliberately.** `RouteAuthorizationTest::test_every_api_route_is_classified` fails on the **first** unclassified route, and `tickets.store` — Story 32's to add — is registered before the new activities route. Classifying only `tickets.activities` would leave the new route unasserted, so Story 39 adds both keys and records it in the PR. **Whichever story lands first adds `tickets.store`; never twice.** After Story 39 the suite carries **one** pre-existing failure (`PasswordThrottleTest`, TM-14) rather than two.

- **Story 39 ships the paginated endpoint but not the append interaction.** TM-49's first two criteria — load-more and event-type filtering — are named and deferred. Story 39 exposes `meta.total` and `meta.last_page` and states in plain words what the reader is seeing, so **TM-49 has nothing to re-plan**.

- **Escaping the audit trail is Story 39's job and no one else's.** Story 29's plan rules that a reason containing `<script>` is stored verbatim because *"escaping is the renderer's job, which is TM-46's"*, and E9-S6's fourth criterion names the timeline explicitly. Story 39 therefore forbids `v-html` outright, verifies it with a `grep`, and asserts a script payload renders as literal text.

- **Story 39 does not remove Story 33's `ticket-resolution` block.** Story 33 rendered AC3's *"prominently in the timeline"* as a dedicated detail-page block precisely because no timeline existed. The two coexist: one is *"how this ticket stands"*, the other *"what happened when"*.

- **Story 40 answers a product question Story 37 deliberately deferred to it.** TM-43's plan (line 50) recorded that an agent investigating for a week through notes alone would see the ticket flagged stale, and handed the decision here: *"the change is one `orWhereExists` … and TM-47 is where that conversation belongs."* **Story 40 honours its own AC4 — a note touches no column on `tickets` — and escalates the trade-off in writing to the backlog owner rather than settling it.** Two tests defend it: one fails if `$ticket->touch()` appears in the controller, one fails if `$touches = ['ticket']` appears on `TicketActivity`. That second edit is the dangerous one: it looks harmless and would silently redefine staleness for **every** activity row.

- **Story 40 is the one story in E7 that adds an event case.** Story 38 adds none, Story 39 adds none, Story 41 (TM-48) adds none. `note_added` fits `varchar(50)` — **no migration anywhere in this epic.**

- **The note body lives in `meta.note`, not `new_value`.** It follows `meta.resolution`'s precedent in the same table (Story 33), and it keeps a 5000-character string out of Story 39's `to_label`, which is computed as `meta.to_name ?? new_value`. For a note, `field`, `old_value`, `new_value`, `from_label` and `to_label` are all **null** — a note is not a field change.

- **Story 40 is the first test of Story 39's extensibility contract, and it passes.** Rendering a note took **one** `DESCRIPTORS` entry, **one** named `eventPhrase` case (the second in the pattern Story 39 established with `created`), one `noteBody` reader, and one template block. **No `switch`, no rewrite.** The one thing the fallback could not supply is a *body block*, because a note's payload is the point rather than a field transition — recorded so the distinction is clear to TM-49.

- **AC2's "escaped" is satisfied at render, not on input, and this is now settled across four stories.** Stories 29 and 34 ruled that a free-text body is stored verbatim and that escaping is TM-46's job; Story 39 implemented it and banned `v-html`. Story 40 stores the note byte-identical and renders it interpolated. **Sanitising on input would corrupt legitimate notes** — `if (a < b)`, `<redacted>` — in a table TM-48 makes unamendable. **The note body is the sharpest instance of E9-S6's fourth criterion**; the PR should name it as such.

- **AC3 ships as a tripwire because there is nothing to exclude notes from yet.** `app/Mail`, `app/Notifications`, `app/Events`, `app/Listeners`, `app/Jobs` and `resources/views/mail` **all do not exist**. A test fakes `Mail` and `Notification` and asserts the endpoint sends and queues nothing — passing today, failing the day mail is wired in. **Excluding notes from a requester mailable stays E8-S3's and E8-S6's criterion**, and the test says so in a comment so a green suite is not mistaken for proof.

- **A note is permanent, and Story 40 says so out loud in three places.** TM-48 makes an activity row unamendable, so an agent cannot fix a typo or retract a note. No criterion mentions this. Story 40 adds no `PATCH`/`DELETE` (TM-48's first criterion would fail), tells the user in the composer (*"Notes are internal and permanent."*), documents it in the API contract, and raises in the PR that an amendable note means a **superseding second row**, never a mutation — a new story that must reconcile with TM-48.

- **`TicketPolicy::addNote` deliberately has no terminal guard.** Unlike `escalate()`, which refuses a terminal ticket, a note on a Closed ticket is the feature working: post-mortem context belongs on the ticket, not in chat. A test asserts `201` on a terminal ticket and **fails if someone "fixes" the policy by copying `escalate()`**. `can.add_note` gates the composer from the server, and the frontend adds no `is_terminal` check of its own.

- **Forward constraint on TM-49: `note_added` is the event its filter was written for.** TM-49's second criterion names *"notes only or status changes only"* by example. Story 40 ships the event; the filter, and append-more-on-demand, stay TM-49's.

- **Story 42 closes the epic, and it is the story every other one in E7 has been deferring to by name.** Stories 39, 40 and 41 each list *"append-more-on-demand"* and *"timeline filtering"* in their **What this story does not build** tables, attributed to TM-49. Story 39 went further and exposed `meta.total` and `meta.last_page` deliberately *"so TM-49 has nothing to re-plan"* — and it did not need to be re-planned. **Every file Story 42 touches is one Stories 39 and 40 created; it creates only two small ones of its own** (`TicketTimelineFilter.vue`, `lib/appendUnique.ts`) and adds **no route, no migration and no event case**.

- **Story 42 adds no route, and that is an assertion rather than a preference.** Story 41's test 17 (`test_the_only_activity_route_is_a_get`) asserts **exactly one** `api/v1` route carries `activities` in its URI, with the comment *"Fails loudly if TM-49 adds a second, which is the moment to re-read AC1."* So the filter is a **query parameter** on Story 39's existing route and the facet rides in the response's `meta` via `->additional()`. `routes/api.php` and `RouteAuthorizationTest::ACCESS` are both untouched, and Story 41's guards keep passing without knowing Story 42 happened.

- **The filter's options come from the ticket's data, because a hard-coded list would break Story 39's contract one layer up.** AC2's own examples are *"notes only or status changes only"* — and `status_changed` is Story 32's, **unimplemented**. A `<select>` with eleven options would ship with nine that return zero rows and would need editing by all nine stories that add an event. Instead the server validates with `Rule::in(TicketActivityEvent::values())` and the response carries `meta.event_counts` — one entry per event type **actually present on this ticket**, with counts. **When Story 32 lands, "Status changed (12)" appears in the filter with no change to either story.** Two tests and a by-hand verification step pin it.

- **The facet deliberately ignores the active filter.** Narrowing `event_counts` to the current selection would collapse the option list to the one type already chosen and leave the reader **no way back**. That single sentence is the subject of one decision and one test in Story 42.

- **Offset append is kept, and Story 42 proves it is lossless rather than assuming it.** On an append-only, newest-first trail (Story 41's guarantee) the only possible mutation between two page requests is *k* rows arriving at the **head**, which shifts the page-2 window *backwards* over rows the client already holds: **repeats are possible, skips are not.** So the client de-duplicates by `id` (`lib/appendUnique.ts`) and Story 39's documented `data`/`links`/`meta` envelope survives intact. Keyset pagination would be strictly more correct and would cost `meta.total`, `meta.last_page` and two shipped plans' documentation — **the reasoning is recorded so a future cursor story finds it instead of re-deriving it.**

- **AC3 is met by bounding the work, not by timing it.** *"Renders without a noticeable delay"* has no assertion in it, and a wall-clock test would be flaky on CI. Story 42 asserts instead that the **query count for a 400-row ticket equals the count for a 3-row ticket** (≤ 5, filtered or not), that the response and the DOM each carry at most `per_page` rows, and that the facet is one `GROUP BY`. It also fixes the one real render cost it found: Story 39's `TicketTimelineEntry.vue` calls `activityReason` **twice per render** — once in the `v-if`, once in the body — which is 1800 calls at 600 entries. Two `computed`s, and Story 39's own rendering tests must pass **unchanged**, which is what proves the refactor changed no output. **No virtual scrolling**: the DOM only ever holds the pages the reader asked for.

- **Two verified traps in one query, both of which fail silently.** The facet must go through `$ticket->activities()` and **never** `DB::table('ticket_activities')` — Story 38's test 21 matches that literal string in source text and fires on a **read**, not just a write. And its aggregate column must be named `aggregate`, **never `event`**: `Builder::pluck()` (`Builder.php:1097–1100`) pushes the plucked *value* column through the model's casts, and `event` casts to `TicketActivityEvent`, so `pluck('event', …)` returns **enum instances** where the client expects `{"created": 1}`. The key column is never cast, which is why `pluck('aggregate', 'event')` is correct.

- **A failed "load more" must not blank the timeline, and that needs a second error ref.** `TicketTimeline.vue` renders `timeline-error` *instead of* the list (Story 39's `v-else-if` chain), so reusing `activitiesError` for an append failure would erase the twenty rows the reader is holding. Story 42 adds `activitiesMoreError`, and the same reasoning gives `activitiesLoadingMore` its own flag — reusing `activitiesLoading` would flash the list away on every press, which is a direct AC4 violation.

- **`loadMoreActivities` reads `latestActivitiesRequest` and never increments it**, which is the opposite of `stores/users.ts:19,30`. Incrementing would make an in-flight append **cancel a ticket switch**; reading means the switch cancels the append. Both directions are tested, because the bug is symmetrical and only one direction is correct.

- **The `makeTicket()` duplication reaches four copies here, and extracting it is a fatal error — not a style call.** Stories 39, 40 and 41 each declare it `private` because there is no `TicketFactory`. PHP forbids reducing an inherited method's visibility, so a `protected makeTicket()` on `Tests\TestCase` stops **three** test classes from loading, at class-declaration time, with an error that looks nothing like its cause. **Story 42 adds a fourth private copy and names the duplication as TM-59's to collapse** when factories arrive and all four call sites disappear together.

- **E7 ships without a single migration, across all five stories.** Story 38 works with the schema TM-21/TM-22 already wrote, Story 40's `note_added` fits `varchar(50)`, Story 41 declines the `restrictOnDelete` change on purpose, and Story 42 declines the `(ticket_id, event, created_at)` index the filtered read would benefit from. **Both declined schema changes are recommendations in a PR with measurements attached**, not silent omissions — Story 41 carries TM-28's `1 → 0` erasure measurement, Story 42 carries an `EXPLAIN` of the filtered read and the facet.

- **With Story 42 the epic is complete and nothing is queued behind it.** `../email-notifications/00-overview.md` is still a stub with no story rows, so Story 42's closing line stops rather than naming a Story 43.
