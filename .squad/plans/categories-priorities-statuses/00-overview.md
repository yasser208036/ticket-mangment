## Dependency notes

- **Story 13 (TM-16) is the entry point for the whole epic and for the data model.** It creates `categories`, `priorities` and `statuses` — the three tables `tickets` points at — so **TM-21** (tickets and requesters schema) is blocked on it, not just TM-17.
- **Story 13 depends on Story 06 (TM-8) being _implemented_, not merely planned.** It copies three decisions from it: the PHP enum as the single definition of an `ENUM` column's domain, the explicit `ENUM` default (TM-8 measured that a `NOT NULL` MySQL `ENUM` with no default silently takes its **first** value while `information_schema` still reports `NULL`), and `AdminUserSeeder`'s "an existing row is left completely alone" contract. TM-8 is done, so this is a read-before-you-write dependency rather than a blocker.
- **Story 13 is backend-only.** It touches no file under `frontend/`, adds no route, controller, form request or API resource, and leaves `backend/routes/api.php`, `backend/bootstrap/app.php` and `backend/.env.example` byte-identical. It cannot conflict with in-flight work in the **authentication-agent** folder.
- **Two contracts every later story in this epic must honour**, both consequences of how acceptance criterion 4 ("exactly one default") is enforced. The guarantee is a **unique index over a virtual generated column** that is `1` for the default row and `NULL` for every other, measured against `mysql:8.4` during planning:
  - **`is_default_unique` must never be written to.** MySQL answers `ERROR 3105 (HY000)` on any attempt, which reaches the SPA as a 500. It is excluded from every `#[Fillable]` and listed in `#[Hidden]`. **TM-59 must not add it to a factory `definition()`, and TM-17/TM-19 must not expose it.**
  - **TM-17 must clear the outgoing default before promoting a new one, inside a transaction.** Setting a second `is_default` fails with `SQLSTATE 23000` / `1062` on `UPDATE` as well as on `INSERT`. Zero defaults is deliberately legal so that clear-then-set has somewhere to stand; the seeders in TM-16 do exactly this and are the pattern to copy.
- **The three seeders are deliberately asymmetric, and TM-17 depends on it.** `CategorySeeder` uses `firstOrCreate` because TM-17 lets admins rename, recolour, reorder and deactivate categories and a seeder that ran on every deploy would silently undo their work; `PrioritySeeder` and `StatusSeeder` use `updateOrCreate` because no story gives priorities or statuses an admin UI, so the code stays the source of truth.
- **`CategorySeeder` must call `withTrashed()`.** Reproduced during planning: MySQL enforces a unique index across soft-deleted rows, so once **TM-18**'s soft delete is used, a plain `firstOrCreate` cannot see the trashed row, tries to insert, and dies with `1062` on `categories_slug_unique`. The seeder must find the trashed category and **leave it trashed** — `restoreOrCreate()` exists but is wrong here, because it would resurrect a category an admin deliberately deleted.
- **Story 13 seeds the seven statuses in the shape TM-37 needs**: `New → Open → In Progress → Resolved → Closed`, with `Pending` in its own bucket reachable from the open states and `Reopened` reachable from the two terminal ones. `bucket` and `is_terminal` are kept **orthogonal** on purpose — TM-40 reopens from either terminal status while TM-41 refuses to escalate either, so folding them into one column would split the rule across two representations.
- **`priorities.level` is unique because TM-41 reads it.** Escalation raises a ticket's priority by looking up `level + 1`, which is only single-valued if no two priorities share a level. It is also the sort key **TM-24** offers on the queue, which is why `priorities` has no `sort_order` column while `categories` and `statuses` do.
- **Hex-colour validation is TM-17's, not TM-16's.** Story 13 deliberately adds no `CHECK` constraint on `color`: a bad hex breaks a badge, not the data model, and a constraint violation surfaces as a 500 rather than the `422` TM-17's acceptance criteria ask for. The column is `char(7)` with a `#6B7280` default; the format rule belongs in TM-17's form request, in one place.
- **Factories for these three models are TM-59's**, so Story 13 adds no `HasFactory` trait and its tests build rows with `Model::create([...])`. TM-59 adds the trait alongside the factory.
- **Story 13 records a defect it does not own.** The backend suite is not green: `Tests\Feature\Auth\PasswordThrottleTest::test_seventh_attempt_is_blocked_per_user` expects `422` and receives `429`, and fails in isolation, so it is a real defect in **TM-14**'s in-flight work rather than cross-test rate-limiter bleed. TM-16's plan pins the baseline at **90 tests / 89 passing** and explicitly forbids fixing it in this story.

- **Story 14 (TM-17) depends on Story 13 (TM-16) being _implemented_, not merely planned** — the hardest blocker in this feature. There is no `Category` model to bind a route to and no `categories` table to query, so **nothing in Story 14 compiles** until TM-16 lands. Confirm with `php artisan db:table categories` before starting.
- **Story 14 is the first story in the project to authorize a route with a policy instead of the `admin` middleware.** Criterion 1 puts categories at `/api/v1/categories` with **reads open to agents and writes restricted to admins** — one path, two answers, which `Route::middleware('admin')` cannot express. `CategoryPolicy` decides instead, which is what `docs/api-contract.md` already promised. Three consequences downstream: `Category` gains the `#[UsePolicy]` attribute TM-16 deliberately omitted; there is **no `Gate::before`** anywhere, so admins get no implicit allow-all; and an unknown category id returns **`404` rather than `403`** to agents, because `SubstituteBindings` resolves before the policy and category existence — unlike a user id — is not a secret.
- **`RouteAuthorizationTest` is a manifest and Story 14 must extend it.** `tests/Feature/Authorization/RouteAuthorizationTest.php:15` maps every `api/v1` route name to `public`/`self`/`admin`, and `test_every_api_route_is_classified` turns red the moment a route is added without an entry. Categories need a **fourth and fifth level** — `staff` and `admin-policy` — because `test_admin_routes_have_three_middlewares` asserts every `admin`-classified route carries the `admin` middleware, which category writes deliberately do not. `routesFor()` also has to learn the `{category}` parameter or `route()` throws `UrlGenerationException`. **This is the most likely task to be skipped, and it is the first thing that will fail.**
- **`Str::slug()` returns an empty string more often than it looks.** Measured on this Laravel version during planning: `北京`, `🌐`, `!!!` and `---` all slugify to `''`, and `Hardware/Software` and `HardwareSoftware` both give `hardwaresoftware` — so a unique **name** does not imply a unique **slug**. Both cases would reach MySQL as `1062` and surface as a **500**. Story 14 catches them in validation as a `422` on `name`. Arabic is *not* a failure case (`الشبكة` → `alshbk`), which matters because the product is utf8mb4 throughout.
- **The slug is generated on create and never regenerated on rename.** TM-16's `CategorySeeder` matches on `slug`, so a slug that moved with the name would make the next `db:seed` create a duplicate row. Both requests mark `slug` as `prohibited` **and** the controller's `safe()->only([...])` excludes it — two independent guards, because the model keeps `slug` fillable for the seeder's benefit.
- **The category list is deliberately unpaginated**, against the convention at `docs/api-contract.md:16`. **TM-19** needs the whole set in one request to resolve an id to a name and colour, and the set is bounded by construction. Story 14 narrows that convention line rather than quietly breaking it.
- **The list returns deactivated categories on purpose, and that is what makes criterion 5 work.** Filtering them out server-side would break the other half of the same criterion — a ticket already carrying a deactivated category still has to render its name and colour. The dropdown filters **client-side**: Story 14's store exposes an `activeCategories` computed, and **TM-22 must read that, not the raw list**. What Story 14 cannot demonstrate is the dropdown itself, which is TM-22's.
- **Three hand-offs out of Story 14:**
  - **TM-18 must _wrap_ `CategoryController::destroy()`, not replace it.** Story 14 ships `DELETE` unguarded because `tickets` does not exist until TM-21, so nothing can be orphaned. **If TM-21 lands before TM-18 there is a real window** in which deleting a category with tickets succeeds — and TM-21's `ON DELETE RESTRICT` does **not** close it, because a soft delete is an `UPDATE` and never trips a foreign key.
  - **TM-19 wraps Story 14's `stores/categories.ts` rather than replacing it.** That store is the admin CRUD store; TM-19's `masterData` store is the app-wide read-only cache, and TM-19's "refreshes without a page reload" criterion is satisfied by subscribing to the admin store.
  - **TM-22 reads `activeCategories`** for the new-ticket dropdown and `CategoryBadge` for display.
- **Story 14 does not backfill TM-12's missing frontend specs.** `src/api/users.ts`, `src/stores/users.ts`, `AdminUsersView.vue` and `UserFormDialog.vue` still have no `.spec.ts`, and `src/api/errors.spec.ts` was never written — TM-12 owns all five. Story 14 does, however, ship a spec for every file it creates, so the omission is not compounded.
- **Story 14 adds no npm dependency.** Criterion 4 says *drag-free* `sort_order` editing, so the screen uses a number input committing on `change` and no drag library. `frontend/package.json` dependencies stay `axios`, `pinia`, `vue`, `vue-router`.

- **Story 15 (TM-18) is hard-blocked on TM-21, now planned as [Story 17](../ticket-creation-tracking/17-story-tickets-and-requesters-schema-TM-21.md) but not implemented.** `grep -rn "category_id" backend/` returns nothing and there is no `create_tickets_table` migration, so there is no `Ticket` model to count and no `tickets.category_id` to reassign. Story 15 cannot start until TM-21 is *implemented*, and it must then ship **immediately after it, in the same sprint** — see the next note for why waiting is not free.
- **TM-21 opens a data-integrity window that only Story 15 closes.** Three probes against `mysql:8.4` in `tm-mysql-test` during planning, on a parent/child pair shaped like `categories`/`tickets` with `ON DELETE RESTRICT`: a soft delete of the parent (`UPDATE … SET deleted_at`) **succeeded** with three children attached, a hard `DELETE` on the same row gave `ERROR 1451`, and an `INSERT` into the child **succeeded** after the parent was soft-deleted. So TM-21's foreign key does not protect anything Story 14's `DELETE` can do, and a trashed category still accepts new tickets. Every day between TM-21 and TM-18 is a day an admin can orphan tickets.
- **The guard needs a lock, not just a count, and the lock works.** Measured: while session 1 held `SELECT … FROM cats WHERE id = 2 FOR UPDATE` inside a transaction, session 2's `INSERT INTO tix (category_id) VALUES (2)` failed with `ERROR 1205 (HY000): Lock wait timeout exceeded`. InnoDB takes a shared lock on the parent row for each child insert's foreign-key check, so `lockForUpdate()` as the transaction's first statement is what makes the ticket count trustworthy. Story 15 requires it in that position.
- **Story 15 absorbs part of TM-45, deliberately and reversibly.** Acceptance criterion 3 of TM-18 ("logs an activity row on every affected ticket") needs `ticket_activities`, which `backlog.json` assigns to **TM-45 in sprint 4** while TM-18 is sprint 2. Story 15 therefore creates the table, `App\Enums\TicketActivityEvent` and `App\Services\ActivityRecorder` **to TM-45's own acceptance criteria, read verbatim from `backlog.json`**, so that **TM-45 extends rather than creates** — more enum cases, the `TicketService` caller, and TM-48's append-only model guards. Roughly 2 points move from TM-45 to TM-18; TM-18's 2-point estimate is wrong as a result. The alternative — re-sequencing TM-18 after TM-45 — drops tasks 1–3 and changes nothing else in the plan, at the cost of leaving the orphaning window open for two sprints. **This is a scope call the team should confirm.**
- **Story 15 changes no route and no route name.** `backend/routes/api.php` stays byte-identical and `RouteAuthorizationTest` is not edited, because the guard rides on the existing `DELETE /api/v1/categories/{category}`. That is a deliberate constraint: the `ACCESS` manifest at line 16 turns red on any unclassified route, and a new `/categories/{category}/reassign` endpoint would have needed a sixth entry and a sixth access level for no gain.
- **`DestroyCategoryRequest` must carry its own `authorize()`, and there is a measurement behind that.** A `FormRequest` resolves and validates **before** the controller body runs, so a request class without one answers `422` where `RouteAuthorizationTest::test_agent_refused_by_policy_admin_routes` demands `403`. Reproduced during planning: that test failed exactly that way on `categories.store` until `StoreCategoryRequest:13` gained `Gate::allows('create', Category::class)`, after which the file passes 12/12. That test already exercises `DELETE` with a real category id and an agent token, so Story 15 inherits the trap.
- **The 422 is a documented superset of Laravel's envelope, not a departure from it.** `message` and `errors` keep their exact shape, so `frontend/src/api/errors.ts` needs no change; `ticket_count` and `reassign_to_options` are added alongside. `docs/api-contract.md`'s conventions bullet (lines 10–11) already allows this "unless a story states otherwise" — Story 15 states otherwise in the place a client will look.
- **Story 15 is labelled `backend` but ships two small frontend tasks, because the guard breaks Story 14's screen.** `frontend/src/stores/categories.ts:55–58` has no `try`/`catch`, so a `422` would reject unhandled and the admin would see the Delete button do nothing at all. Story 15 widens `deleteCategory(id, reassignTo?)`, adds a `deleteBlockedBy()` reader in `api/categories.ts` (not in the shared `errors.ts`), and adds one `CategoryDeleteDialog.vue`. Nothing else under `frontend/` changes.
- **Story 14 landed its sources without its tests, and Story 15 does not backfill them.** The backend suite went from 90 to 93 between TM-16 and today, and all three new tests are in `RouteAuthorizationTest`; there is no `backend/tests/Feature/Categories/` directory and no `.spec.ts` for `api/categories.ts`, `stores/categories.ts`, `AdminCategoriesView.vue`, `CategoryFormDialog.vue` or `CategoryBadge.vue`. TM-17 owns that gap. Story 15 ships a test for every file it creates, so the omission is not compounded.
- **Story 15's baselines**: backend **93 tests / 92 passing** (the one red test is still TM-14's `PasswordThrottleTest`, `422` vs `429`, failing in isolation and explicitly out of scope), frontend **24 tests across 6 files**.

- **Story 16 (TM-19) is labelled `frontend` and opens with five backend tasks, because two of the three lists it caches have no API.** `grep -rn "priorit\|statuses" backend/routes/ backend/app/Http/ docs/api-contract.md` returns nothing and `route:list` shows ten routes, none of them for priorities or statuses. **No story in `backlog.json` creates them** — E3 is four stories and none of the other eight epics mentions such an endpoint — so `GET /api/v1/priorities` and `GET /api/v1/statuses` are TM-19's to ship. Without them acceptance criterion 1 is unreachable, and **TM-22** hits the same wall when it needs a priority dropdown.
- **Both new endpoints are read-only and get no policy.** `CategoryPolicy` exists because categories carry admin-only writes on the same path; priorities and statuses have no writes at all, so `auth:sanctum` plus `active` is the whole authorization story and both routes are classified `staff` in the manifest. Consistent with TM-16's decision that priorities and statuses are code-owned master data with no admin UI.
- **`RouteAuthorizationTest` bites again, and one of its tests is weaker than it looks.** `test_every_api_route_is_classified` turns red the moment either route is registered without an `ACCESS` entry. Separately, `test_agent_reaches_staff_routes` (line 52) hard-codes `/api/v1/categories`, so it would have gone on passing without ever touching the new routes — Story 16 widens it to loop `routesFor('staff', $category->id)`, which `routesFor()` already supports via the `$categoryId` parameter TM-17 added.
- **Two stores, not one, and `stores/categories.ts` stays.** The TM-17 store is an admin CRUD store with a `status` filter that reloads on every mutation; `masterData` is an app-wide, unfiltered, write-free cache loaded once. The overview note from Story 14 stands: TM-19 wraps rather than replaces.
- **Story 16 inverts the refresh direction Story 14 recorded.** Story 14's note said `masterData` would subscribe to the admin store; Story 16 has the admin store call `masterData.refreshCategories()` instead. Subscribing would mean calling `useCategoriesStore()` inside `masterData`'s setup, instantiating the admin CRUD store for every agent on every page and pointing the app-wide store at an admin-only one. Specific depends on general. The cost is one extra unfiltered `GET /categories` per admin mutation, because the admin list is filtered and cannot feed the cache.
- **`masterData.activeCategories` supersedes the admin store's.** Story 14's overview told **TM-22** to read `activeCategories` from `stores/categories.ts`; **that is now wrong** — the admin store's list is filtered by whatever the admin screen last selected and is empty on every page that is not `/admin/categories`. **TM-22 and TM-24 read `masterData.activeCategories`.**
- **The cache is reset from `useAuthStore().clear()`, and that is the only complete place.** `logout()` and the `401` handler in `guards.ts` both funnel through it; resetting inside `logout()` alone would leak a revoked or deactivated session's master data into the next account on the same browser.
- **The prefetch is fired, not awaited, so `ensureLoaded()` is contractually forbidden from rejecting.** `authGuard` calls it with `void` before its final `return true`; a rejected floating promise is an unhandled rejection in the browser and a failed Vitest run. `refresh()` uses `Promise.allSettled` so one dead endpoint cannot blank the other two lists, and `loaded` flips only when all three succeed, so the next navigation retries.
- **`guards.spec.ts` breaks on contact and must be edited in the same commit.** Its only mock covers `../api/auth`; once the guard touches master data, the authenticated tests issue real axios requests inside jsdom. Three `vi.mock` factories fix it.
- **Criterion 2 is a contract, not a refactor, so Story 16 makes it enforceable.** Audited 2026-08-26: the only `<select>` in the SPA is `AdminCategoriesView.vue:30–33` with three literal options, `CategoryBadge.vue` takes a prop and issues no request, and `stores/users.ts` fetches users. **There is nothing to convert** — the first real dropdown is TM-22's. Story 16 therefore adds `masterData.contract.spec.ts`, a manifest test that fails by filename when any source outside `stores/masterData.ts` and `stores/categories.ts` imports `listCategories`, `listPriorities` or `listStatuses`.
- **The lookup helpers return `CategoryBadge.vue`'s exact prop type** (`{ name, color, is_active }`) so a resolved id drops into the existing badge with no adapter, and they never return null — an absent id yields a muted `Unknown` / `#6B7280` badge. **Priority and status badge components are not built**: there is no screen to render them on until **TM-24** (queue) and **TM-26** (ticket detail), which own them. `CategoryBadge.vue` is left byte-identical.
- **Story 16 and Story 15 are independent in both directions.** Story 15 changes `CategoryController::destroy()`, `deleteCategory()` and `remove()`'s signature; Story 16 touches none of them. Either order works, and Story 16's plan says how its mutation hook composes with Story 15's `remove(id, reassignTo?)`.
- **Story 16 corrects one stale sentence in `docs/api-contract.md` that TM-17 owns.** Lines 27–28 still read "Category and ticket policies arrive with their models in TM-17 and TM-22", which is now false; Story 16 edits that same paragraph and rewrites it rather than leaving a provably wrong statement beside a new one. TM-17's other outstanding doc work — the missing `### /api/v1/categories` section — is **not** backfilled.
- **Story 16's baselines**: backend **93 tests / 92 passing** (the red one is still TM-14's `PasswordThrottleTest`, out of scope), frontend **24 tests across 6 files**. No new npm or composer dependency; `@pinia/testing` is deliberately not added — store specs use `createPinia()` plus `vi.mock`, as `HealthView.spec.ts` already does.

- **Story 17 (TM-21) claims `Category::tickets()`, which Story 15 task 5 also specifies.** The method is identical in both plans; Story 17 claims it because it creates the foreign key. **Whichever lands second must check before writing it.** Story 17 also confirms the handshake on migration order: its `create_tickets_table` must sort before Story 15's `create_ticket_activities_table`.
