# status-workflow-escalation — plan overview

Entry point for the **status-workflow-escalation** feature. Stories execute in order by their `NN` prefix. `NN` continues the global sequence that runs through [`../foundation-environment/00-overview.md`](../foundation-environment/00-overview.md), [`../authentication-agent/00-overview.md`](../authentication-agent/00-overview.md), [`../categories-priorities-statuses/00-overview.md`](../categories-priorities-statuses/00-overview.md), [`../ticket-creation-tracking/00-overview.md`](../ticket-creation-tracking/00-overview.md) and [`../assignment-workload/00-overview.md`](../assignment-workload/00-overview.md).

## Dependency notes

- **Story 37 is backend-only, needs no other story in this epic, and its command name and unit were already fixed before it was planned.** `backend/.env.example` already ends with `TICKETS_STALE_AFTER_HOURS=48` and a comment naming `php artisan tickets:flag-stale` — **hours, not days** — while `grep -rn "TICKETS_STALE" backend/app backend/config` returns nothing and there is no `config/tickets.php`. The variable has been orphaned since the environment story wrote it. **Story 37 wires up the variable that already exists rather than inventing a second one.**

- **"Last activity" is `tickets.updated_at`, and TM-47 is the reason.** E7-S3's fourth criterion is *"Adding a note does not change the ticket status or its `updated_at` semantics for staleness"* — a note must not reset the clock, which rules out defining staleness from the activity trail. The tension is recorded rather than hidden: an agent investigating for a week without changing a field will see the ticket flagged. **If notes should count, that is one `orWhereExists` and it is TM-47's conversation, not a quiet redefinition in the command.**

- **Idempotency is a query, not a column.** A `stale` row whose `created_at >= tickets.updated_at` blocks a re-flag; no `stale_flagged_at` column and no migration. It gets the semantics right for free — a ticket flagged, worked on, then abandoned again *should* be flagged twice, and a boolean column would have to be cleared by every write path in the app. Writing the `stale` row does not bump `tickets.updated_at` (different table), which is what makes the rule stable.

- **Measured, and Story 37 adds no index.** The exact query, on 60 tickets: `statuses` (7 rows, driving) → `tickets` via **`tickets_status_id_index`** (`type=ref`) → `ticket_activities` via **`ticket_activities_timeline_index`** (`type=ref`, `Not exists`). TM-21's and TM-45's existing indexes already serve it. **Counter-intuitively, adding `index(updated_at)` — the index Story 20 will add for its own sort — made the plan worse**, switching `tickets` to a `type=ALL` hash join. Recorded as an observation at an unrepresentative 60 rows, not a rule: **do not add, drop or reorder any index for this story.**

- **A backlog gap Story 37 found: no E8 story owns a stale-ticket digest.** E8-S1…S7 cover queue infrastructure, assignment, creation, requester status changes, **escalation**, the shared layout and the queueing rules — none mentions staleness. So `stale_notify` dispatches a single `TicketsFlaggedStale` event per run with **no listener anywhere in the backlog**, and `TICKETS_STALE_NOTIFY` therefore defaults to **false**. **Either E8 gains a story or the flag stays off** — writing an unqueued mailable here would be deleted by E8-S7.

- **The most likely production failure of Story 37 is not in its code.** The scheduler entry is inert unless the host cron runs `php artisan schedule:run` every minute, and nothing reports its absence. That line is the reason task 7 adds a `## Scheduled tasks` section to `docs/deployment-runbook.md` — whose `_TBD_` placeholders stay untouched for **TM-63**. `onOneServer()` is deliberately not set: it needs a cache shared between app servers and this project has no deployment topology decided.

- **Story 36 is the most blocked story in the epic, and half of what its acceptance criteria describe is already built by other stories.** The `escalated` filter (API parameter, URL key and `filter-escalated` select) is **Story 20's**; the `escalated` stat and the `stat-escalated` card are **Story 25's**; `escalation_level` and `escalated_at` are already in the list payload via `TicketResource`. **Story 36 must not rebuild any of it** — its plan opens with a "what is already delivered" table naming the owner of each half, and four of its tests exist purely as regressions on that seam. What is genuinely new is the badge, the `escalated_at` sort, its index, and one link fix.

- **Story 36 fixes a real cross-story defect in Story 25's dashboard.** The `stat-escalated` card's figure is scoped — an agent's card counts only their tickets — and its *label* already follows `scope`, but its **link does not**: `escalatedTo` is a plain `?escalated=true`. So an agent sees "My escalated tickets: 3", clicks, and lands on every escalated ticket in the queue. Story 36 makes the link a computed that appends `assignee: 'me'` when `scope === 'own'`, using Story 20's existing URL sentinel. **Story 25's spec assertion on that href is amended, not duplicated.**

- **Measured, and the `escalated_at` index rests on it.** `ORDER BY escalated_at DESC, id DESC LIMIT 15` on 60 rows: without an index `type=ALL, key=NULL, Using filesort`; with `index(escalated_at)` `type=index, Backward index scan`. **The identical profile Story 20 measured for `updated_at`, and the same fix** — in its own migration, leaving both `create_tickets_table` and Story 20's migration untouched.

- **MySQL orders NULL below any value, so `sort=escalated_at&direction=desc` puts never-escalated tickets last for free.** Measured. **The sort must not become a filter**: no `IS NULL` clause, no `whereNotNull`. Story 36's verification step 6 adds one and requires a test to fail, which is the guard against someone "tidying" it later.

- **The escalation badge carries the level in its text as well as its colour.** Amber-vs-red is one of the worst pairs for a colour-blind reader, so "Escalated" versus "Escalated ×N" is what actually satisfies AC4 and the colour reinforces it. **Never `×1`** — a bare "Escalated" is the level-1 signal. The two hex values are Medium's and Urgent's from `PrioritySeeder`, so the queue reads as one palette.

- **The badge is for the list only; TM-41's detail-page escalation section is untouched.** That section already states the level in prose with the reason and the actor, and a second signal on a page with room for the sentence is noise.

- **Story 35 is the one story in this epic that does not depend on the workflow guard.** Escalation changes `escalation_level`, `priority_id` and `assigned_to` and **never `status_id`**, so it goes nowhere near `TicketWorkflow` or `status_transitions`. It reads only `statuses.is_terminal`, seeded since TM-16. **If Stories 31–34 slip, Story 35 can still ship** — its only hard dependency is TM-26, already in the tree, and the only file it shares with them is `TicketActivityEvent`, where every story appends.

- **Story 35 moves `TicketPolicy::escalate()`'s terminal check to the handler, and that is not a reversal of Story 22.** Story 22 shipped `escalate()` as `! $ticket->status->is_terminal` and its overview says *"TM-41 must keep that check."* **AC5 of TM-41 requires a `422`, and a denied policy can only ever be `403`** — the exact string `RouteAuthorizationTest.php:40` asserts. So the policy becomes a pure role gate, the state check moves into the handler **under the row lock**, and `can.escalate` on the detail response folds both together so the button still hides. **This is Story 27's split, for the same reason.** Verification step 4 reverts each half in turn and requires a *different* test to fail — that is how the plan guarantees neither half was lost.

- **A terminal ticket is the only `422` in this epic that is checked under a lock rather than validated.** It cannot live in the form request: a ticket someone else resolved a moment ago must be caught after the lock, not before it.

- **Escalation routes to the active admin with the fewest open tickets, ties broken by lowest id.** Lowest-id-only would send every escalation in the system to one person from day one; round-robin needs persistent state for a tie-break a `COUNT` answers better. "Open" is `is_terminal = false`, the definition E5 fixes product-wide. **The actor is not excluded** — an admin escalating a ticket they hold keeps it and still gets the level and the priority. Story 35 adds `User::assignedTickets()` for the count, **the relation TM-35 needs too**, added once here rather than twice.

- **No active admin is a `422` with nothing written, not a silent unassign.** Escalating into an empty queue would report success while quietly breaking AC3. `CategoryController::reassignmentRequired()` (78–84) is the established shape for "this operation needs a target and there is none".

- **Two activity rows, and the second only when the assignment actually moved.** The `escalated` row alone satisfies AC4; the companion `assigned` row exists because E5 requires assignment history to be reconstructable from `ticket_activities`, which means every assignment change must be findable by **`field = 'assigned_to'`** — the same audit rule Story 34 fixed for `status_id`. It is written in Story 26's exact shape, and Story 35 adds `TicketActivityEvent::Assigned` **only if Story 26 has not**.

- **No `priority_changed` event is invented here.** The priority move lives in the `escalated` row's meta only, so **priority history is not field-keyed for escalations**. **TM-27 (edit a ticket) owns `priority_id` history and has not named its event yet** — it decides whether escalation owes a companion row, and the meta already holds the data. Inventing the name here would force TM-27 to match it.

- **`escalation_reason` is current state; the trail is history.** A second escalation overwrites the column and both reasons stay in `ticket_activities`. Story 35 asserts it so the split is deliberate rather than discovered by whoever first wonders where the old reason went.

- **Story 35 discharges Story 22's toolbar contract in full.** `action-escalate` is the fourth and last of the four disabled buttons TM-26 shipped with `title` placeholders. Its test 29 asserts **no button carries a placeholder any more**, which is how the next reader knows that contract is closed.

- **Story 34 adds no endpoint: reopening is a status transition.** It goes through Story 32's `POST /tickets/{ticket}/status` with `status_id` = Reopened and a required `reason`. A dedicated `/reopen` route would have to re-derive "may this ticket be reopened" — the question Story 31's graph exists to answer as data — or skip it. **Contrast with `/assign` and `/claim`, which are separate endpoints on purpose**: those change a field the graph knows nothing about.

- **Story 34 also arrives with AC1's first half already done.** Story 31 seeds `resolved → reopened` and `closed → reopened`, both ungated, and its plan records that `closed → reopened` was deliberately *not* made admin-only because TM-40 is written for an agent. **Story 34 adds only "and requires a reason".**

- **A reopen writes ONE row and its event is `reopened`, not `status_changed` — and the cost is paid for explicitly.** AC3 says "a reopened activity row", TM-46's timeline wants its own icon per event, and the reopen count becomes an exact `where event = 'reopened'`. The invariant that breaks is "every status change is a `status_changed` row". The mitigation is that the reopen row fills `field`, `old_value` and `new_value` **identically**, so the surviving invariant is: **every status change is exactly one row with `field = 'status_id'`; only the event name differs. Query status history by `field`, never by `event`.** Story 34's test 6 and verification step 6 exist solely to keep that true, and it is written into the API contract.

- **Story 34 narrows Story 32's test 4 and deletes Story 33's `test_reason_is_still_prohibited`.** The first now claims "one `status_changed` row per **non-reopen** move"; the second is superseded because `reason` stops being unconditionally prohibited. **Amend them, do not leave both.**

- **The badge and the count are deliberately two signals.** `ticket-reopened-badge` keys on the **current status** ("what is this ticket now"); `ticket-reopen-count` keys on the number and shows whenever it is above zero, **including after the ticket has moved on** ("has this been round before"). Deriving the badge from the count would badge a ticket that was reopened last March and closed since.

- **`reopen_count` is computed with `loadCount` in `show()`, not in the resource — the first change to `show()` since Story 32 left it alone.** `allowed_transitions` and `resolution` depend on the caller; a count is a plain aggregate of a relation the model should have anyway. Story 34 therefore adds `Ticket::activities()`, the model's first `HasMany` — **the relation TM-46's timeline endpoint needs too**, added once here rather than twice.

- **Story 34 replaces the growing tail of optional strings with one options object.** Story 33 widened `changeTicketStatus(id, statusId, resolution?)`; a fourth positional `reason?` would make the reopen call read `(id, s, undefined, reason)`. It becomes `changeTicketStatus(id, statusId, { resolution?, reason? })` — a three-call-site refactor if Story 33 lands first, recorded in the PR so it does not read as unrelated churn.

- **10–5000 characters is now the bound for every free-text justification in the workflow.** Story 33 set it for `resolution`, Story 34 reuses it for `reason`, and **TM-41's escalation reason should too** — one number a reader learns once instead of three each defending itself.

- **A reopened ticket keeps its assignee, its priority and its escalation level.** Nothing in the AC asks otherwise, and Story 34 pins it with a test so the first person who assumes reopening should unassign has to argue for it. Notifying on reopen is E8's, not this story's.

- **Story 33 takes TM-40's clearing clause, and TM-40 must not re-implement it.** TM-40's second criterion — *"Reopening clears `resolved_at` and `closed_at`"* — is the same rule as TM-39's AC2, and `resolved_at` cannot ship correctly without it: a reopened ticket still advertising a resolution date is simply wrong. **TM-40 keeps the reopen reason, the reopened badge and the reopen count.** Story 33 also leaves `reason` `prohibited` with its TM-40 message intact.

- **Story 33 expresses the clearing rule as `! $to->is_terminal`, never as the `reopened` slug.** Only `resolved` and `closed` are seeded terminal (`StatusSeeder.php:17–18`), and the only edges out of a terminal status lead to `reopened` — so the two readings agree today. Keying on the column means an edited graph cannot leave a reopened ticket carrying a stale resolution date. Verification step 7 proves it by flipping `is_terminal` and watching the test fail.

- **AC3's "rendered prominently in the timeline" is rendered on the detail page, because there is no timeline.** `GET /tickets/{ticket}/activities` and every timeline component are **TM-46** (E7-S2). Story 33 ships the storage half in full — `meta.resolution` on the `status_changed` row, the exact key TM-46 will read — and renders a dedicated `ticket-resolution` block instead. **TM-46 renders the same row inline and does not remove that block**: one says how the ticket stands, the other what happened when. This is Story 29's split with one deliberate difference — a reassignment reason is a history fact, a resolution is a current-state fact.

- **No `tickets.resolution` column, on purpose.** "The current resolution" is the note attached to the move that produced the ticket's current `resolved_at`, so AC2 and AC3 are the same rule from two sides: `resolved_at` null means no resolution and costs zero queries. A column would be a second source of truth that has to be re-decided after every reopen.

- **Three slug constants, and no `requires_note` column on `statuses`.** `tickets` has carried `resolved_at`, `closed_at` and `first_responded_at` as columns since TM-21, so the schema already committed to those three slugs being product vocabulary. Story 33 puts them in `Status::SLUG_NEW` / `SLUG_RESOLVED` / `SLUG_CLOSED` and grep-verifies they appear nowhere else in `backend/app`. **Which moves are legal stays data; what three statuses mean is code.**

- **Story 33 deletes Story 32's `test_no_timestamp_is_stamped` and splits its `test_resolution_and_reason_are_prohibited`.** Story 32 wrote the first as a scope fence and named TM-39 as its executioner. **Replace them, do not leave both.**

- **A ticket created directly into a non-New status never gets a `first_responded_at`.** `POST /tickets` accepts `status_id` (`StoreTicketRequest.php:37`) and creation is not a transition, so such a ticket can reach Resolved with the column still null. Recorded and pinned by a test as intentional — **do not "fix" it in `store()`**; if the product wants otherwise, that is a change to creation, not to the stamping rule.

- **Story 32 is the story that makes Story 31 visible, and it cannot start before it.** Every guard it calls lives in files Story 31 creates. Its gate is `php artisan test --filter='TicketWorkflowTest|StatusTransitionSeederTest'` green.

- **Story 32 adopts `tickets.store` into `RouteAuthorizationTest::ACCESS`, fixing a baseline failure TM-22 left behind.** That test has been red since TM-22 added the route without classifying it. Story 32 is the story editing that array, so it adds both `tickets.status` and `tickets.store` as `staff` and takes the suite from 3 failures to 2. **Recorded so TM-22 does not add a duplicate key later.**

- **The status response omits `can` and `allowed_transitions`, and the SPA re-reads the detail — the same decision Story 26 made for assign.** Both keys are stale the instant the status moves: `allowed_transitions` changes wholesale and `can.escalate` flips on a terminal status (`TicketPolicy.php:45–48`). Because both sit behind the existing `routeIs('tickets.show')` gate, the omission costs zero new conditionals. **Do not collapse it into one round-trip** — TM-40's reopen would inherit the trap.

- **`allowed_transitions` is a per-caller affordance on `tickets.show` only, and it costs two queries.** Measured while planning: eager-loading `show()`'s seven relations costs **5 queries on an unassigned ticket and 6 on an assigned one**, because `assignee`, `creator` and `escalatedBy` all target `users` and an eager load with an empty key list issues nothing. Story 32 pins the full-request count at exactly two more than whatever it measures.

- **A filtered dropdown is not enforcement, and Story 32 tests both halves separately.** The admin-only `resolved → closed` edge is absent from an agent's `allowed_transitions` **and** refused by `assertCanTransition()` when an agent posts it anyway. Either test alone would pass an implementation that is wrong.

- **Story 32 carries a scope fence for TM-39: `test_no_timestamp_is_stamped`.** `resolved_at`, `closed_at` and `first_responded_at` are already columns and it would be one line to stamp them here. **TM-39 is the story that deletes that test and replaces it** — nothing before it writes a timestamp.

- **Story 32 writes the two frontend spec files TM-26 never did.** `frontend/src/components/TicketActionToolbar.spec.ts` and `frontend/src/views/TicketDetailView.spec.ts` do not exist. It creates both rather than assuming TM-26 will come back for them, and asserts that the other three toolbar buttons are **still** disabled with their titles.

- **Story 31 is backend-only and adds no route.** It ships a table, a seeder, a model, a service and tests. `POST /api/v1/tickets/{ticket}/status`, the detail-response `allowed_transitions`, the `status_changed` activity row and every line of SPA code are **TM-38**. Because it registers no route, it cannot affect `RouteAuthorizationTest::ACCESS`, and the baseline failure there stays TM-22's.

- **The seven status slugs are fixed by TM-16 and Story 31 does not add an eighth.** `StatusSeeder.php:12–20` seeds `new`, `open`, `in-progress`, `pending`, `resolved`, `closed`, `reopened`; the transition graph's vertex set is exactly those. TM-16's plan already anticipated this story by name (*"TM-37 builds `status_transitions` on the status ids"*).

- **"Active state" means `is_terminal = false`, never `bucket = 'open'` — the same reading E5 adopted.** `pending` has its own bucket and is still on someone's plate, so Pending is reachable from `new`, `open`, `in-progress` **and** `reopened`. Story 31 also seeds `pending → open` and `pending → in-progress`, which the acceptance criteria do not ask for: without them a ticket parked on a customer is unresolvable forever. `test_no_status_is_a_dead_end` is what stops a later story deleting them.

- **`resolved → closed` is the single admin-gated edge, and the choice was forced by TM-40.** AC5 needs a seeded `required_role = admin` edge to be testable, and the obvious candidate — `closed → reopened` — is disqualified because **TM-40 is written for an agent** (*"As an agent, I want to reopen a resolved or closed ticket"*). Nothing in TM-39 says who may close, so closing is where the second pair of eyes goes. **TM-39 must not re-litigate this**; if the team changes its mind it is one seeder row and no PHP.

- **Every workflow refusal is a `422`, never a `403`, and TM-38 depends on that.** `TicketPolicy::changeStatus()` already answers *may this user operate the status control* (yes, all staff — `TicketPolicy.php:40–43`); whether a specific edge is available is a property of the request body. TM-38's fifth criterion — *"A rejected transition surfaces the server message rather than a generic error"* — is unimplementable against a `403`, which renders as the fixed string `This action is unauthorized.` The SPA reads `errors.status_id[0]`, one error path.

- **TM-38 owns the row lock, and Story 31 cannot supply it.** `TicketWorkflow` only reads; it deliberately carries no `DB::transactionLevel()` guard, unlike `TicketReferenceGenerator` and `ActivityRecorder`. TM-38 must call `assertCanTransition()` **inside** its own transaction, after `lockForUpdate()`, or two concurrent requests can both pass the guard and one illegal write lands.

- **From TM-38 onward, `db:seed --class=StatusTransitionSeeder` is a required deploy step.** A migrated-but-unseeded table rejects *every* status change with a message indistinguishable from correct enforcement. Story 31 records it; the deployment runbook (E9) must carry it once the endpoint exists.

- **The seeder prunes, unlike `StatusSeeder`.** `db:seed` restores the default graph exactly and removes hand-added edges. Without pruning, an edge removed from `EDGES` would survive every re-seed and the lifecycle could only ever be loosened, never tightened — the exact failure the guard exists to prevent. Consequence recorded rather than hidden: a runtime graph change belongs in `EDGES` and a deploy.

- **TM-41 reads `statuses.is_terminal` and `priorities.level`, not this table.** Escalation is orthogonal to the transition graph: it raises priority and routes to an admin without moving the status. `TicketPolicy::escalate()` already enforces the terminal check (`TicketPolicy.php:45–48`). **Do not route escalation through `TicketWorkflow`.**

- **TM-39 and TM-40 add the side effects, not new guards.** `resolved_at`, `closed_at` and `first_responded_at` are already columns on `tickets` (`create_tickets_table.php:29–31`); Story 31 writes to none of them and adds no `TicketActivityEvent` case. Those stories hang stamping and clearing off TM-38's endpoint, above the guard.

- **A badge TM-38 owes E5.** [`../assignment-workload/00-overview.md`](../assignment-workload/00-overview.md) records that Story 28's `mine_open` count is refreshed on assignment events and that **TM-38 must add the same `stats.load()` call** after a status change, or the badge goes stale when a ticket is resolved or closed. Not Story 31's concern — it has no frontend — but it is the epic's inherited obligation.

- **Story 31's tests still work around the missing `TicketFactory` (TM-59, owned by Story 19).** `backend/database/factories/` holds only `UserFactory.php`. The workflow tests build tickets with a local `ticketAt()` helper using `Model::create` and the seeded master data, the same way Stories 17 and 18 did. **If `TicketFactory` has landed by then, use it and delete the helper** rather than adding a second variant.
