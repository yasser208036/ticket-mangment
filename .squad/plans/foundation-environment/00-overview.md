## Dependency notes

- **Story 01 (TM-2) is the entry point for the whole project.** It runs `git init`, hardens the root `.gitignore`, writes the root `README.md`, and creates the three `docs/` placeholders. Every later story assumes the repository is under version control.
- **Story 02 (TM-3) depends on Story 01.** It writes the `GET /api/v1/health` contract into `docs/api-contract.md`, which Story 01 created as a placeholder, and adds a `pdo_mysql` row to the root `README.md` prerequisites table that Story 01 wrote.
- **Story 02 carries an environment prerequisite that is not a code change:** the `pdo_mysql` PHP extension is missing on the development machine (`PDO::getAvailableDrivers()` returns only `pgsql`), so `php artisan migrate` fails with `could not find driver` and `/api/v1/health` returns `503`. Task 1 of Story 02 installs it and needs `sudo`. Nothing downstream of Story 02 can touch the database until that is done.
- Story 01 touches no application source: `backend/app/`, `backend/routes/` and `frontend/src/` are untouched, so it cannot conflict with work in the **authentication-agent** feature folder.
- Story 02 touches no `frontend/` file and adds no migration, so it cannot conflict with TM-4 (Vue SPA) or with the schema stories (TM-8, TM-16, TM-21). It does change the meaning of the health payload's `version` key and adds an `api` key — **TM-4 must code against the contract in `docs/api-contract.md`, not against the pre-TM-3 response.**
- Story 02 deliberately leaves three documented-but-unimplemented `.env.example` blocks in place, annotated with their owning stories: `ADMIN_*` → **TM-8**, `TICKETS_STALE_AFTER_HOURS` → **TM-43**, `DB_TEST_*` → documentation of the test container (`phpunit.xml` hard-codes the real values).
- **Story 03 (TM-4) depends on Story 02 being _implemented_, not merely planned.** Two reasons, both hard: until TM-3 installs `pdo_mysql` the health endpoint returns `503`, so TM-4's acceptance criterion "the SPA successfully calls `/api/v1/health` and renders the result" cannot be demonstrated; and TM-3 **changes the response shape** (`version` becomes the app version, the API version moves to a new `api` key), which is the shape TM-4's `HealthResponse` interface is typed against.
- Story 03 touches **no file under `backend/`** and adds **no npm dependency** — everything its acceptance criteria need (`axios`, `pinia`, `vue-router`, `vitest`, `jsdom`, `@vue/test-utils`) is already in `frontend/package.json`. It leaves `docs/api-contract.md` to TM-3.
- Story 03 establishes three seams later stories plug into, and stops there: `src/api/token.ts` (a plain `localStorage` module, **not** a Pinia store, because axios interceptors run before `createPinia()`) for **TM-9**'s auth store to wrap; `src/views/LoginView.vue` and the `login` route for **TM-9**/**TM-11** to fill in; and `setUnauthorizedHandler` in `src/api/client.ts`, injected from `main.ts` to avoid a router↔client import cycle. **TM-9 must also update `LOGIN_PATH` in `src/api/client.ts`** if it registers the login route at anything other than `/auth/login` — otherwise the 401 redirect guard stops matching and a failed sign-in redirects to itself.
- Story 03 makes `/` the health view as a sprint-1 landing page; **TM-29** replaces it with the dashboard. `createWebHistory` means a production web server must rewrite unknown paths to `index.html` — that rule belongs to **TM-63**.
- **Story 04 (TM-5) depends only on Story 01 (TM-2)**, which wrote both files it edits (`docker-compose.yml` and the root `README.md`). It is **independent of Stories 02 and 03** and can run in any order relative to them: it touches no file under `backend/` or `frontend/`.
- Story 04 is an **audit-and-close**, not a greenfield build. `docker-compose.yml` already ships all three services, named volumes and interpolated variables, so three of TM-5's five acceptance criteria are already met (named volumes; Mailpit reachable with Laravel's `MAIL_*` pointing at it; start/stop documented). Two are not: there is **no root `.env`/`.env.example`**, so every `${…:-default}` resolves to its default and `DB_ROOT_PASSWORD`, `MAILPIT_SMTP_PORT` and `MAILPIT_UI_PORT` are documented nowhere; and the README has no **reset** sequence.
- **Story 04 fixes a reproduced defect in the MySQL healthcheck.** `mysqladmin ping -h localhost` connects over the unix socket, so it passes against the entrypoint's temporary `--skip-networking` init server: `docker compose ps` reports `healthy` up to ~1.5 s before port 3306 opens, and `composer setup`'s `php artisan migrate --force` fails in that window. `mysqladmin ping` also exits `0` on *access denied*, so the password in the test string proved nothing. The replacement connects **over TCP as the application user to the application database** using the container's own environment. This is a behaviour change worth knowing about downstream: a credential changed against an existing volume now surfaces as **`unhealthy`** instead of passing silently.
- **Story 04 must not change any Compose default** — the constraint Story 02's plan already recorded (line 487). `backend/phpunit.xml:36-39` hard-codes `127.0.0.1`, `3307` and `ticket_management_test` and reads no Compose variable, so a drifted default breaks `composer test` with a connection error rather than a failed assertion. The plan's verification pins this: `docker compose config` output must be byte-identical with and without a root `.env`.
- Story 04 pins `axllent/mailpit:latest` to **`v1.31.0`** and declares Mailpit's healthcheck in the compose file. Mailpit reports `healthy` today only because the *image* ships a `HEALTHCHECK`; nothing in this repository promised it. It deliberately adds **no volume** to Mailpit — captured mail lives in `/tmp` and is throwaway.
- Story 04 adds **no automated test**, by design: the assertions worth making are about the environment the suite runs in, not about application code. **TM-6** owns automating the stack check as part of the CI pipeline and will consume these healthchecks as its service-readiness gate.
- **Story 05 (TM-6) depends on Stories 02 (TM-3) and 03 (TM-4) being _implemented_, not merely planned** — a hard blocker on two lines of the workflow. `composer test` exits `1` today on the `@no_additional_args` token TM-3 removes, and `frontend/package.json` has no `test` script until TM-4 adds one, so the CI jobs would be red for reasons that have nothing to do with CI. **Story 04 (TM-5) is _not_ a blocker**: CI uses a GitHub Actions service container, not `docker-compose.yml`.
- Story 05 reuses TM-5's healthcheck finding rather than repeating its mistake. The CI service container probes with `mysqladmin --protocol=TCP … status`, measured to exit `0` on correct credentials and `1` on wrong ones, because `ping` exits `0` even on *access denied* and `-h localhost` passes against the entrypoint's `--skip-networking` init server. The command is also deliberately free of nested quotes — GitHub passes `options:` to `docker create` verbatim.
- **Story 05 adds no dependency to either side.** Every lint and format package is already installed (`eslint@10.9.1`, `eslint-plugin-vue@10.10.0`, `@vue/eslint-config-typescript@14.9.0`, `@vue/eslint-config-prettier@10.2.0`, `prettier@3.9.6`, `laravel/pint@1.30.5`), and `@eslint/js` is **not** installed — a flat config importing it dies at module resolution, which is why the config uses `globalIgnores` from `eslint/config` (part of ESLint itself). `frontend/package-lock.json` must be unchanged.
- **Story 05 configures Prettier to match the code, and does not reformat anything.** Prettier's defaults (double quotes, semicolons) fail on five files today — and on **every code block Story 03 prescribes**, which is written single-quote/no-semicolon throughout. With exactly `{"semi": false, "singleQuote": true}` the whole tree passes with zero rewrites (verified). Reformatting instead would have put the linter at odds with this feature's own plans.
- **Story 05 corrects `CLAUDE.md`**: lines 42–43 cite `npx vitest run src/components/HelloWorld.spec.ts`, a file that has never existed and whose component Story 03 deletes, and line 88 says there is no ESLint config. Lines 30–31 (the Pint commands) were already correct and stay untouched.
- **`APP_VERSION` is reassigned from TM-6 to TM-63.** Story 02's plan hands it to TM-6 in three places (lines 165, 450, 486) as "set from the release tag in CI", but Story 05's CI has **no build or deploy job** — nothing is published and there is no environment to publish to, so there is nothing for the value to label. Injecting it into the test job would be actively wrong: `phpunit.xml` does not read it, and TM-3's health test sets it per-test so the assertion cannot pass against a matching default. **TM-63** owns it along with the rest of deployment.
- **Story 05 also notes an intake defect worth carrying to the tracker:** TM-6's first acceptance criterion names `php artisan pint --test`, and no such Artisan command exists in Laravel 13 (`php artisan list` has nothing matching `pint|lint|format|style`). The real command, `./vendor/bin/pint --test`, already passes over 31 files. The plan uses it everywhere and adds a `composer lint` alias rather than writing a wrapper command to satisfy the wording.
- **TM-5 must keep the frontend dev-server port at 5173** — Story 03 pins it with `strictPort` because `FRONTEND_URL` and `SANCTUM_STATEFUL_DOMAINS` in `backend/.env` both name it. Story 04's plan touches no frontend port.
- With Story 05 planned, **every story in the foundation-environment feature has a plan**. Nothing further is outstanding in this folder.
