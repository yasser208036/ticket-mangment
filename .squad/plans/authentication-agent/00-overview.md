## Dependency notes

- **Story 06 (TM-8) is the entry point for this feature and for the whole schema.** It is the first story to write a table, the first to use `RefreshDatabase`, and the first to make `phpunit.xml`'s comment about ENUM columns load-bearing. Every later story in E2 authenticates against the table it creates.
- **Story 06 depends on Story 02 (TM-3) being _implemented_, not merely planned** — a harder blocker than usual. `pdo_mysql` is missing on the development machine (`PDO::getAvailableDrivers()` returns only `pgsql`), so `php artisan migrate` cannot run at all, and `composer test` exits `1` before PHPUnit starts. **Not one command in Story 06's test plan can execute until TM-3 lands.** Stories 04 (TM-5) and 05 (TM-6) are not blockers.
- **Story 06 edits the existing `create_users_table` migration in place** rather than adding a second migration. Verified safe: `SHOW TABLES` in both `ticket_management` and `ticket_management_test` returns nothing, so no database anywhere holds the old shape — and because `pdo_mysql` is absent, nobody *can* have migrated. Once a teammate has migrated, the only fix is `php artisan migrate:fresh --seed`, which destroys local data.
- **`users.role` defaults to `agent`, and the default is a security control, not a convenience.** Measured on MySQL 8.4: a `NOT NULL` `ENUM` with no explicit default silently stores its **first** value while `information_schema.COLUMN_DEFAULT` still reports `NULL`. `UserRole::Admin` is declared first, so without `->default(UserRole::Agent)` every insert that forgot to set a role would create an **administrator**. Any later story that adds a role-bearing column must repeat the explicit default.
- **`role` is deliberately not mass-assignable.** `#[Fillable]` covers `name`, `email`, `password` and `is_active` only, and Story 06 adds a test asserting the exclusion. **TM-12** must set `role` explicitly when creating or editing an agent — `User::create($request->validated())` with a `role` key would be a privilege-escalation path. Factories are unaffected: `Factory::makeInstance()` runs inside `Model::unguarded()`.
- **`is_active` is enforced nowhere after Story 06.** The column, the cast and the factory state exist; no code reads them. **TM-9 must reject a login where `is_active` is false**, and **TM-10 / TM-11** must not treat a still-valid token as proof of an active account — a deactivated agent's existing token keeps working until someone revokes it. This is the most important hand-off out of Story 06.
- **Credentials reach the seeder through `config('seeding.admin.*')`, never `env()`.** `env()` returns `null` once `php artisan config:cache` has run, so a seeder calling it directly works on every developer machine and fails on the first cached deploy. Story 06 creates `backend/config/seeding.php` — the project's first non-framework config file. `ADMIN_PASSWORD` has **no default** there: the seeder throws rather than create an administrator whose password is published in this repository.
- **The admin seeder never overwrites an existing account.** It is keyed on email and returns early when the user exists, so a changed password and a manual deactivation both survive a re-seed. `updateOrCreate` would revert both on every `migrate --seed` — Story 06 tests against that specifically.
- Story 06 provides the factory states **TM-9 through TM-14** will build their tests on: `->admin()`, `->agent()` and `->inactive()`, with `agent` as the unstated default so a test needing elevated rights has to say so. **TM-59** (Factories and a demo seeder) owns anything richer than that, and owns the demo data `DatabaseSeeder` deliberately does not create.
- Story 06 opens `docs/erd.md` with the `users` entity and the owning-story row. **TM-16** (master data) and **TM-21** (tickets and requesters) add the rest of the diagram; the placeholder note at the top of that file stays until they do.
- **`CLAUDE.md` is left alone by Story 06 on purpose.** Its claim that the project has "the default user table" goes stale, but TM-6 is already editing that file this sprint and a second story touching it is a merge conflict for no benefit. Whoever implements TM-6 or TM-9 should fold the correction in.

Confirmed not done at planning time: `grep "role\|is_active"` on the users migration returns nothing and `app/Enums/` does not exist.

That is Story 07's regression baseline, and `tests/Feature/HealthTest.php` is now the **local test precedent** every later backend story should match (`test_it_…` names, `RefreshDatabase`, chained `assertJson*`).

Every validation and throttling test passes without it; only the success path 500s.
- **A generic error message is not a generic response.** Measured at the configured cost: `Hash::check` costs **287.9 ms** at `BCRYPT_ROUNDS=12`, and short-circuiting it for an unknown email costs `0.000 ms`. Story 07 therefore spends one `Hash::make` on the missing-user path so the timing cannot enumerate valid addresses. Anyone reviewing that line as "a useless hash" reintroduces the oracle, and the 5-per-minute limit does not compensate.

Story 07 pins it with a test asserting the two full response bodies are *identical*, so changing it later has to be a conscious decision.

Do not "fix" the missing entry in TM-10 or TM-11 either.

Story 07 adds a **named** `login` limiter (`Limit::perMinute(5)->by($request->ip())`) in `AppServiceProvider::boot()` and applies it to the one route. Note the failure mode: an unregistered named limiter throws `MissingRateLimiterException` — a 500 on the first request, not a silently unthrottled route. Throttling the rest of the API is **TM-64**.
- **Story 07 creates two namespaces the whole API will use:** `App\Http\Requests\Api\V1\…` and `App\Http\Resources\V1\…` (neither directory exists today), plus `App\Http\Controllers\Api\V1\Auth\` for TM-10 and TM-14. `UserResource` becomes the single definition of "the user object" — **TM-11** should type its SPA store against it and **TM-12** should return collections of it rather than raw models.

Story 07 leaves `config/sanctum.php` untouched.

Story 07 creates exactly that path, named `auth.login`. Renaming it to `/login` or `/auth/token` silently breaks the SPA's redirect guard into a loop.
- Story 07 touches **no file under `frontend/`** and adds **no dependency** — `laravel/sanctum v4.3.3` is installed and `personal_access_tokens` already has its migration, so `composer.json` and `composer.lock` must be unchanged.

- **Story 08 (TM-10) depends on Story 07 (TM-9) being _implemented_, not merely planned.** Confirmed not done at planning time: `routes/api.php` still has exactly one route, `app/Http/` contains only `Controllers/`, and `app/Models/User.php:18` is still `use HasFactory, Notifiable;`. Without TM-9 there is no way to obtain a token, so not one test in Story 08 can run.
- **`Sanctum::actingAs()` cannot test logout, and fails by passing.** Measured against the installed tree: `Sanctum::actingAs()` attaches `Mockery::mock(PersonalAccessToken::class)->shouldIgnoreMissing(false)` (`Sanctum.php:72`), and `shouldIgnoreMissing(false)` makes every un-stubbed call return `false` instead of throwing (`Mockery/Mock.php:349-355`, `1091-1101`). `currentAccessToken()->delete()` therefore returns `false`, writes nothing, and the endpoint still answers `204` — the test asserts half of acceptance criterion 1 and none of criterion 2, because no real token exists to replay. Story 08 bans the helper from all four of its test files and pins the ban with row-count assertions. It stays fine for **TM-12** and **TM-13**, which need an authenticated user but never touch the token itself.
- **Logout deletes one token; deactivation deletes all of them.** `currentAccessToken()->delete()` in `LogoutController` honours TM-9's multi-device decision (signing out on a phone leaves the laptop signed in, pinned by TM-9's `test_it_does_not_revoke_existing_tokens`); `tokens()->delete()` in `EnsureUserIsActive` is correct because there the account, not the session, is being cut off. A `tokens()->delete()` slip in the controller passes both the `204` test and the `401` replay test — only the surviving-token assertion catches it.
- **Story 08 closes the "existing-token door" TM-8 and TM-9 both left open, and it is a deliberate widening of TM-10's stated scope.** TM-10's three acceptance criteria say nothing about `is_active`; Story 08 adds `App\Http\Middleware\EnsureUserIsActive` anyway, because this is the first story in the project to create authenticated routes and therefore the first — and cheapest — chance to make the check something TM-11 through TM-14 inherit by adding a route to an existing group. Without it, `GET /auth/me` returns a full `200` user object to someone an administrator has just disabled, since `config/sanctum.php` `expiration` is still `null`. **If that task is dropped, TM-12 inherits both the middleware and the token revocation, and this note has to be rewritten at the same time.**
- **The middleware answers `401` and revokes, rather than `403`.** Once the tokens are deleted the caller genuinely holds no credential, so `401` is honest; more practically, `frontend/src/api/client.ts:28` acts on `401` only — a `403` would leave the SPA showing an error screen with a dead token still in `localStorage`. Revoking on the way out also means deactivation costs one refused request instead of recurring forever. **TM-12 must still call `$user->tokens()->delete()` when an admin deactivates an account**: the middleware is the backstop that bites on the user's next request, TM-12's delete is what cuts access the moment the admin clicks the button.
- **`Route::middleware(['auth:sanctum', 'active'])->group(...)` in `routes/api.php` is the artefact Story 08 is really delivering.** TM-11's guarded routes, TM-12's admin endpoints, TM-13's policy-checked actions and TM-14's password change all belong **inside** that group. Story 08 adds a test that walks the route table and asserts every `auth.*` route except `auth.login` carries both middlewares, so a later story that adds a protected route beside the group fails a test rather than shipping unguarded. Order matters: `auth:sanctum` first, because `active` reads `$request->user()`.
- **Story 08 makes the first-ever edit to `bootstrap/app.php`'s `withMiddleware`**, which has been an empty `//` stub since TM-3. Adding an alias is safe — `Middleware::getMiddlewareAliases()` is `array_merge(defaultAliases(), customAliases)` (`Foundation/Configuration/Middleware.php:793-796`), so `auth`, `throttle` and the rest survive, and TM-9's `throttle:login` is unaffected. Verify with `route:list --columns=method,uri,name,middleware` rather than by reading.
- **`/auth/me` returns `{"user": …}`, not `{"data": …}`.** It reuses the exact line from TM-9's `LoginController` so the SPA parses one shape from both endpoints and **TM-11**'s Pinia store needs a single type. The stated cost: `data` remains the wrapper for resource *collections*, so **TM-12**'s paginated user list will be `{"data": […], "links": …, "meta": …}`. The convention — auth endpoints name their payload, resource endpoints use `data` — is written into `docs/api-contract.md`'s `## Conventions` block by Story 08. **Do not** set `JsonResource::$wrap = null` globally to make them match.
- **Applying Sanctum's `EnsureFrontendRequestsAreStateful` would break logout.** `Guard::__invoke()` tries the `web` session guard before the bearer token (`Guard.php:32-38`) and hands a session-authenticated user a `TransientToken`, which implements only `can()` and `cant()` — `->delete()` on it is a fatal "call to undefined method". Unreachable today because `bootstrap/app.php` never applies that middleware, which is the concrete reason `routes/api.php:12` says there is no session. If **TM-11** ever proposes cookie-based auth, this is the line item it has to answer for.
- **Story 08 adds no migration, no dependency and no config change.** `config/sanctum.php` stays untouched (`expiration` still `null`) and `config/auth.php` is not edited. Token expiry, token prefixes, pruning and API-wide throttling all remain **TM-64**'s, and they need no change to these endpoints — an expired token fails `Guard::isValidAccessToken()` and surfaces as the same `401` Story 08 already returns.
- Story 08 touches **no file under `frontend/`**. The logout button, the auth store and the route guards are **TM-11**; `client.ts`'s existing `401` interceptor already does the right thing with both of Story 08's failure responses.

- **Story 09 (TM-11) is the first frontend story in this feature, and the first story anywhere in the plan set whose blockers are on the other side of the stack.** It consumes `POST /auth/login` (TM-9), `POST /auth/logout` and `GET /auth/me` (TM-10) and adds nothing to them, so `git status --short backend/ docs/` must stay clean. Confirmed at planning time that neither backend story has landed: `routes/api.php` still has exactly one route and `User` still lacks `HasApiTokens`.
- **Story 03 (TM-4) *is* implemented** — verified live, not assumed: `src/main.ts` wires Pinia, the router and `setUnauthorizedHandler`; `src/api/{client,token,health}.ts`, `src/router/index.ts`, `src/stores/health.ts` and both views exist; `npm run test` passes with **3 files / 11 tests** and `npm run typecheck` exits `0`. That is Story 09's regression baseline, and `src/stores/health.spec.ts` plus `src/views/HealthView.spec.ts` are now the **frontend test precedent** every later SPA story should match — real Pinia (`@pinia/testing` is **not installed**), module-scope `vi.mock` of the API module, `data-testid` selectors, and the compressed several-statements-per-line style there is no Prettier config to reformat.
- **The rehydration race is the story's central problem, and it is a race rather than a lookup.** On reload `localStorage` holds the token but not the user, so a guard that checks `auth.user` throws an administrator out on every refresh. The guard must `await` hydration, and hydration must be memoised: measured with vue-router 4.6.4, **returning a redirect from a guard re-runs the guard** — `guardCalls 2` for a single `router.push('/')` — so an un-memoised `GET /auth/me` is two requests per page load. Any later story that adds work to `beforeEach` inherits that doubling.
- **The hydration promise lives as a plain `let` inside the `defineStore` setup callback.** Measured: that scope is per-Pinia-instance, so `setActivePinia(createPinia())` resets it and the "one `/auth/me` for three concurrent callers" test is genuinely isolated. At module scope the same code works in the browser and makes that test pass or fail depending on spec file order. **TM-19** (cache master data in a Pinia store) has the same shape of problem and should copy the placement, not re-derive it.
- **The token is persisted; the user is deliberately not.** A cached user goes stale in exactly the ways TM-10 and TM-13 care about — an admin demoted to agent keeps an admin UI, a deactivated agent keeps a rendered app — and `GET /auth/me` exists precisely so a client holding a token can ask who it is. The cost is one extra request per page load and a first paint that waits on it. `localStorage` holds **only** `tm.token`, and `src/api/token.ts` stays the single module allowed to touch storage. **Do not** add `pinia-plugin-persistedstate` in a later story to "fix" this; it is not installed and the omission is the design.
- **Routes are private by default from Story 09 onward.** The guard checks `to.meta.public`, a whitelist, rather than `to.meta.requiresAuth`, a blacklist — so **TM-12**, **TM-22**, **TM-23** and **TM-26** cannot accidentally ship a world-readable screen by forgetting a meta key; a forgotten key makes the route private, which someone notices immediately. After Story 09 the public list is exactly one record, `login`, and an integration test iterating `router.getRoutes()` asserts that. **`meta: { public: true }` on `/login` is load-bearing**: without it the guard redirects `/login` to `/login`.
- **Augmenting `RouteMeta` buys value checking, not typo protection.** Measured: `meta: { role: 'superuser' }` fails with `error TS2322`, and `to.meta.public` becomes `boolean | undefined` instead of `unknown` — but `meta: { publik: true }` **compiles cleanly**, because `interface RouteMeta extends Record<PropertyKey, unknown>` upstream in vue-router. The route-table test, not the type system, is what catches a mis-keyed record. Do not write a comment claiming otherwise and do not try to remove the index signature.
- **`?redirect=` is sanitised, and the sanitiser cannot be tested through the router.** Measured against vue-router 4.6.4: `resolve('https://evil.com')` yields `/https://evil.com` — the scheme is neutralised — but `resolve('//evil.com')` yields `//evil.com` **verbatim**, which a browser reads as protocol-relative and follows off-site. `safeRedirect` rejects `//`, `/\`, anything without a leading `/`, and non-strings (a repeated query key arrives as `string[]`). **jsdom does not reproduce the browser's protocol-relative resolution** — pushing `//evil.com` under jsdom stayed same-origin — so the assertions live on `safeRedirect` directly; a test that "proves" the router is safe would pass either way.
- **Acceptance criterion 4 is two requirements, and the existing half-implementation is the wrong half.** `main.ts:9`'s `router.currentRoute.value.name !== 'login'` is not a double-redirect guard: `currentRoute` only changes when a navigation **resolves**, so two `401`s in one tick both navigate. Story 09 replaces it with a latched handler built by a factory (fresh latch per call, so specs need no reset) and asserts `router.replace` was called **once**. vue-router's own duplicate detection is a silent backstop only — measured, a duplicated `replace` resolves with a `NavigationFailure` of type `16` rather than throwing.
- **`/auth/login`, `/auth/me` and `/auth/logout` are exempted from the `401` interceptor.** All three answer `401` as part of normal operation, and two of them do so at the worst moment: `/auth/me` fails *while the guard is awaiting it*, so an interceptor redirect cancels the in-flight navigation and loses the `?redirect=`; `/auth/logout` was already revoked by TM-10's design, and the component is already navigating. The rule is "the interceptor rescues a request that did not expect a dead session". **TM-14 must not widen this to a prefix match on `/auth/`** — a `401` from its `POST /auth/password` genuinely means the session died mid-form and the interceptor should react.
- **A `401` throws the token away; a timeout does not.** `isAuthenticated` is `user !== null`, not `token !== null`, so a stored token whose `/auth/me` timed out sends the user to the sign-in form while keeping the token — the API coming back means they are signed in again with no password. Every later story reading `isAuthenticated` gets that distinction for free.
- **The store never navigates; the guard never fetches.** `stores/auth.ts` imports `api/auth.ts` and mutates state; `router/guards.ts` imports the store and returns a route; components call an action then navigate themselves. The one non-component navigation is the `401` handler, which lives in `guards.ts` and takes the router as an argument rather than importing it — which is also what makes it unit-testable. Keep the direction one-way in **TM-12** onward.
- **`router/index.ts` gains a `createAppRouter(history?)` factory** and calls `installAuthGuards` inside it, so a test router is guarded identically to the real one. This exists because importing the module-level singleton into two spec files shares accumulated history **and** one globally-installed `401` handler on the shared axios client, making failures depend on file order. Later frontend specs should use the factory with `createMemoryHistory()`.
- **Story 09 ships two deliberate stubs, both following TM-4's precedent of a real route with a placeholder component.** `/` stays on `HealthView` and becomes private — **TM-29** replaces the component, not the route. `/admin/users` gets `meta: { role: 'admin' }` and a one-paragraph placeholder — **TM-12** replaces the component. The route meta is the deliverable; without an admin-only route, acceptance criterion 3 cannot be demonstrated at all.
- **`meta.role` is not authorization.** It hides a screen. **TM-13**'s policies decide what the API will do, and an agent who types an admin endpoint's URL gets a `403` from the server regardless of what the SPA rendered. No later story may treat a passing guard as permission.
- **Cross-tab sessions are knowingly unhandled, and no story owns them.** The store seeds its token from `getToken()` once, so signing out in one tab leaves another tab rendering until its next request `401`s — correct but late. A `window.addEventListener('storage', …)` bridge is the fix if it ever becomes a complaint; Story 09 does not add one.
- **Story 09 adds no dependency and changes no configuration.** `frontend/package.json`, `package-lock.json`, `vite.config.ts`, `tsconfig*.json`, `.env.example` and `src/env.d.ts` must all be unchanged. **TM-6 landed after Story 09 was planned**, so there are now four frontend gates rather than two — `npm run format`, `npm run lint`, `npm run typecheck` and `npm run test` — with `.prettierrc.json` set to `{"semi": false, "singleQuote": true}`. Because `tsconfig.app.json` sets `noUnusedLocals`, an unused import in a spec breaks the build while `vitest` still passes. Run all four.

- **Story 10 (TM-12) is the first story in the project to touch both sides of the stack in one go**, and the first CRUD screen. Its four backend endpoints sit under `/api/v1/admin/users`; its frontend replaces the `AdminUsersView.vue` placeholder Story 09 shipped. Stories 06–09 were all **done** by the time it was planned, so it is the first consumer of TM-8's `role`/`is_active` columns, TM-9's `UserResource`, TM-10's `['auth:sanctum', 'active']` group and `active` alias, and TM-11's auth store and admin route.
- **Acceptance criterion 1's ticket count is deliberately not shipped, and no column of zeros stands in for it.** There is no `tickets` table — `database/migrations/` holds four files and none of them creates one; `tools/jira/backlog.json` puts the tickets schema in **TM-21** (E4-S1), two epics later. A stub table here would collide head-on with TM-21's real schema (the readable reference, the FULLTEXT index, the `ON DELETE RESTRICT` foreign keys `phpunit.xml:27-35` exists to test). **TM-21 owes exactly four lines**: a `tickets()` relation on `User`, `->withCount('tickets')` in `UserController::index`, `'tickets_count' => $this->whenCounted('tickets')` in `UserResource` (`whenCounted`, so the field never appears on the login or `/auth/me` responses), and a `tickets_count?: number` plus one `<th>`/`<td>` on the frontend. Story 10's frontend test asserting **no** ticket-count column is what forces that story to change the test deliberately.
- **"An admin cannot deactivate or demote their own account" is not the invariant that matters.** Two admins deactivating each other in the same instant both pass the self-check and both read "two active admins" from an unlocked count: **zero administrators**, every `/admin/*` route `403` for everyone, recovery only via `artisan tinker`. Story 10 therefore enforces two rules — the self-check for the ordinary mistake, and a **last-active-admin** check that survives concurrency because it holds `lockForUpdate()` inside `DB::transaction()`. That is why the rule lives in the controller and **not** in `UpdateUserRequest`: a validator runs and returns before any transaction opens, so a count read there is exactly the read that races. A reviewer who moves it for tidiness reopens the hole.
- **Both lockout refusals are `ValidationException`, not `abort(403)`** — so they arrive as `422` with the message on `errors.is_active` or `errors.role`, and Story 10's dialog renders them under the right control with no special-casing. The memo lives as a plain `let` inside the `defineStore` setup callback, because a second probe confirmed that scope is per-Pinia-instance — a fresh `createPinia()` restarts the counter at 1 — whereas module scope works in the browser and silently couples the "one request for three concurrent callers" test to spec file order.
  Two more behaviours were measured rather than assumed. **`?redirect=` is an open-redirect surface vue-router does not close**: `resolve('https://evil.com')` neutralises the scheme to `/https://evil.com`, but `resolve('//evil.com')` passes it through verbatim, and a browser follows a leading `//` off-site — while **jsdom does not reproduce that resolution**, so the sanitiser's tests assert on the function directly instead of pretending the router proves anything. And **augmenting `RouteMeta` buys value checking, not typo protection**: `meta: { role: 'superuser' }` fails with `TS2322`, but `meta: { publik: true }` compiles cleanly because `RouteMeta extends Record<PropertyKey, unknown>` upstream — so an integration test iterating `router.getRoutes()`, not the type system, is what catches a mis-keyed record. A duplicated `router.replace` was also confirmed to resolve with a `NavigationFailure` of type `16` rather than throw, which is why the "exactly once" assertion spies on `replace` instead of relying on that backstop.
  Three design decisions follow from the findings and are recorded above rather than left implicit: routes are **private by default** (a whitelist, so a forgotten meta key makes a route private rather than public), the **token is persisted but the user is not** (re-fetched every page load so a role change or a TM-10 deactivation cannot be stale), and `/auth/login`, `/auth/me` and `/auth/logout` are **exempt from the `401` interceptor** because all three answer `401` as part of normal operation and two do so while a guard is mid-flight.
  The plan is nine tasks — 6 files created, 4 edited, **42 tests** across five new spec files plus two added to `client.spec.ts`, taking the frontend suite from 11 to **53** — with no dependency, no config change, and no file touched under `backend/` or `docs/`. Two stubs ship deliberately, both following TM-4's precedent of a real route with a placeholder component: `/` keeps `HealthView` and becomes private (**TM-29** replaces the component) and `/admin/users` carries `meta: { role: 'admin' }` behind a one-paragraph placeholder (**TM-12** replaces the component). Without that second route, acceptance criterion 3 cannot be demonstrated.
