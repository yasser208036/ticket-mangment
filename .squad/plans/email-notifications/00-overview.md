# email-notifications — plan overview

Entry point for the **email-notifications** feature. Stories execute in order by their `NN` prefix. `NN` continues the global sequence that runs through [`../foundation-environment/00-overview.md`](../foundation-environment/00-overview.md), [`../authentication-agent/00-overview.md`](../authentication-agent/00-overview.md), [`../categories-priorities-statuses/00-overview.md`](../categories-priorities-statuses/00-overview.md), [`../ticket-creation-tracking/00-overview.md`](../ticket-creation-tracking/00-overview.md), [`../assignment-workload/00-overview.md`](../assignment-workload/00-overview.md), [`../status-workflow-escalation/00-overview.md`](../status-workflow-escalation/00-overview.md) and [`../ticket-history-audit-trail/00-overview.md`](../ticket-history-audit-trail/00-overview.md).

## Dependency notes

- **Story 43 is an audit-and-close, not a greenfield build, and the audit is the point.** Measured on 2026-08-27: `config('queue.default')` is already `database`, `0001_01_01_000002_create_jobs_table.php` already created `jobs`, `job_batches` and `failed_jobs` in batch 1, and a queued `Illuminate\Mail\Mailable` went `jobs=1` → `queue:work --once` → captured by Mailpit in 520 ms. **Two of the four acceptance criteria are already satisfied by code nobody wrote for this story.** What is missing is a guarantee (AC2), a document (AC3) and tests. Whoever executes it should resist rebuilding what already works.

- **The test suite currently contradicts AC1, and that is the single most consequential line in the epic.** `phpunit.xml:45` forces `QUEUE_CONNECTION=sync`, so a queued mailable executes **inline inside the request** during `composer test`. TM-52's fifth criterion (*"a feature test asserts the notification is queued rather than sent synchronously"*) and TM-57's first (*"no notification is sent inline during a request"*) are both unimplementable against that. Story 43 flips it to `database`. **It is safe to flip today and will never be safer** — `grep -rn "ShouldQueue\|dispatch(\|->queue(" backend/app backend/database backend/routes` returns nothing, so no existing test can regress. From Story 43 onward, a test that dispatches something and expects its side effect must `Queue::fake()`, drive `queue:work --once`, or assert the `jobs` row.

- **"No mail leaves the machine" was a convention, not a rule.** README.md:121–122 has claimed it since TM-2, but nothing stopped a `.env` from pointing `MAIL_MAILER` at SES or `MAIL_HOST` at a real relay. Story 43 makes it enforced: `App\Services\MailSafety` listens on `Illuminate\Mail\Events\MessageSending` and **throws** unless the transport is `log`/`array` or SMTP on a host in `MAIL_SAFE_SMTP_HOSTS`.

- **The guard checks the transport, never the recipient — because TM-52, TM-54 and TM-55 all have to assert the recipient.** A domain allowlist or `Mail::alwaysTo()` would rewrite or reject exactly the field those stories need to read back out of Mailpit. **Do not add address filtering to this guard later**; a guard that destroys the evidence is worse than no guard.

- **It runs at send time, not at boot, and it must never return `false`.** `Mailer::shouldSendMessage()` (`Mailer.php:602–609`) dispatches `MessageSending` through `until()` and treats `false` as *cancel this message silently* — a green request with no email, which is worse than an exception. The listener is a block closure declared `: void` for that reason. Send-time also means the guard runs **inside the queue worker**, a separate process a boot-time check in the web app would never reach, and it avoids bricking every artisan command when a `.env` is wrong.

- **`MAIL_URL` overrides `MAIL_HOST` silently** (`config/mail.php:43`), so the guard resolves the host from the DSN when one is set. A version that only read `host` would wave `MAIL_URL=smtp://…@smtp.sendgrid.net:587` straight through. `failover` and `roundrobin` are recursed into for the same reason — the shipped `roundrobin` fans out to `ses` and `postmark`, neither of them safe.

- **Production is deliberately unguarded, and it is written down twice.** `guarded_environments` is `['local', 'testing']`; mail has to work in production. Story 43 pins it with a test and states it in `docs/deployment-runbook.md` so nobody "hardens" the guard into blocking real mail.

- **Story 43 does not touch `tries`, `backoff` or `after_commit` — TM-57 owns all three.** `config/queue.php:44` still reads `'after_commit' => false`, which is precisely TM-57's fourth criterion (*"notifications dispatch after the database transaction commits"*). Flipping it in the infrastructure story would silently pre-empt the story written to reason about it. Story 43 records the numbers (`retry_after` 90, no job timeouts yet) instead of setting a policy it does not own.

- **`composer dev` has been running a queue worker all along and nobody documented it.** `composer.json:45–48` maps it to `php artisan dev`, and `Illuminate\Foundation\DevCommands.php:99` registers `queue:listen --tries=1 --timeout=0` alongside `serve`, Pail and Vite. Two consequences Story 43 writes into the README: **do not start a second worker on top of it**, and **`--tries=1` means a failing job goes straight to `failed_jobs` with no retry under `composer dev`** — which will otherwise be discovered by whoever debugs TM-57's retry policy.

- **The one mechanism in Story 43 not yet proven in-process is `queue:work --once` inside PHPUnit.** It was measured working from the CLI in both directions (success → Mailpit; failure → `failed_jobs` with the exception, then `queue:retry`). Inside a test the worker shares the process and the `RefreshDatabase` transaction, so it should see the same rows — but that test is the one to run first, and the plan names the fallback rather than allowing a quiet downgrade to `Queue::fake()`.

- **A backlog gap this epic still has not closed: no story owns a stale-ticket notification.** [`../status-workflow-escalation/37-story-flag-stale-tickets-on-a-schedule-TM-43.md`](../status-workflow-escalation/37-story-flag-stale-tickets-on-a-schedule-TM-43.md) dispatches `TicketsFlaggedStale` with **no listener anywhere in the backlog**, which is why `TICKETS_STALE_NOTIFY` defaults to `false`. TM-51…TM-57 cover infrastructure, assignment, creation, requester status changes, escalation, the layout and the queueing rules — **none of them mentions staleness.** Story 43 does not fill the gap; **either E8 gains a story or the flag stays off.**

- **Story 44 is one listener and one notification, because Story 29 already shipped the rule.** [`../assignment-workload/29-story-reassign-or-unassign-with-a-reason-TM-34.md`](../assignment-workload/29-story-reassign-or-unassign-with-a-reason-TM-34.md) split TM-34's third criterion across two sprints on purpose: it delivers `App\Events\TicketAssigned`, dispatched **once per real assignment, after the transaction commits, never on unassign**, and its plan says outright *"TM-52's remaining job is one listener and one mailable."* **Story 44 must not re-derive who is notified or when** — that contract is settled, tested with `Event::fake()` in sprint 3, and re-litigating it would produce two sources of truth for the same rule.

- **The self-assign guard lives in the listener, and Story 29 asked for it there by name.** AC3 (*"No email is sent when a user assigns a ticket to themselves"*) is currently **unreachable over HTTP** — `/assign` is admin-only and requires an active **agent** target, and Story 27's `/claim` deliberately dispatches nothing. Story 29 recorded that *"if that rule is ever relaxed, TM-52's criterion is where the guard belongs."* Story 44 puts `if ($event->assigneeId === $event->actorId) return;` in the listener, the one place every producer passes through, so the rule survives a future endpoint that forgets. Its test drives the **event** rather than the endpoint, because the endpoint cannot reach the case.

- **The notification is queued; the listener is not.** Queueing both would make one assignment push a listener job that pushes a notification job. `ShouldQueue` on the notification alone produces exactly **one** `SendQueuedNotifications` row, which is what the AC5 test counts. No `ShouldQueueAfterCommit` either — Story 29 already dispatches outside the transaction, and **TM-57 owns that guarantee product-wide**, along with `tries`, `backoff` and `timeout`, none of which Story 44 sets.

- **AC5 cannot be tested with `Notification::fake()`, and that is why Story 43 is a hard gate.** The fake intercepts before the queue, so `assertSentTo` passes identically for a queued and a synchronous notification. The real test uses no fake at all: assign, assert **zero** messages on the array transport and **one** row in `jobs`, then run `queue:work --once` and assert the message arrives. **That test fails under `phpunit.xml`'s current `QUEUE_CONNECTION=sync`** — which is precisely the line Story 43 changes.

- **`MailMessage`, not a bespoke Blade layout — and TM-56 loses nothing by it.** Measured while planning: a rendered `MailMessage` produced **an 11,676-byte HTML part and a 463-byte plain-text part** with **no `mail.markdown` key in `config/mail.php`**, and its text part opened with `config('app.name')` and `config('app.url')`. So TM-56's *"every email has a plain-text alternative part"* and *"the from address, product name and base URL all come from configuration"* are already true for this shape. **Extracting a shared layout from one example is guesswork; TM-56 does it with four.**

- **Measured trap for every E8 story: markdown emphasis does not survive into the text part.** `->line('**Reference:** …')` renders literally as `**Reference:**` in plain text. **Every field line in an E8 email is plain `Label: value`.**

- **The deep link is `{frontend_url}/tickets/{id}` on the numeric primary key, never the reference.** `frontend/src/router/index.ts:52` declares `/tickets/:id` and `TicketDetailView.vue:9` loads with `Number(route.params.id)`, so a reference-based URL produces `loadTicket(NaN)`. The **subject line still leads with the reference**, because that is the string a human quotes. Story 44 adds `config('app.frontend_url')` because `FRONTEND_URL` is currently reachable only through `env()` in `config/cors.php:22`, and **`env()` returns `null` once config is cached**. `config/cors.php` keeps its own `env()` call and is not edited — a config file must not call `config()`.

- **Category is the one relation in an assignment email that can be null.** `tickets.requester_id`, `category_id`, `priority_id` and `status_id` are all `NOT NULL` with `restrictOnDelete`, but **`Category` soft-deletes** (`Category.php:41`), so `restrictOnDelete` does not stop `$ticket->category` resolving to `null`. Story 44 eager-loads it `withTrashed()`. **Every later E8 story that names a category owes the same load.**

- **`readonly` promoted properties on a queued notification are safe, and it was measured rather than assumed.** `SerializesModels::__unserialize()` restores state with `ReflectionProperty::setValue()` on a constructor-less object; on **PHP 8.3.6** a readonly property accepts exactly one such write. Measured separately: `hasDefaultValue()` is **`false`** for promoted properties, so `__serialize`'s skip-the-default branch cannot silently drop a `null` `$reason`.

- **`$this->seed()` with no argument throws in this suite, and every E8 test must know it.** `DatabaseSeeder` calls `AdminUserSeeder` first, which aborts on an empty `ADMIN_PASSWORD`, and `phpunit.xml` never sets one. Seed `CategorySeeder`, `PrioritySeeder` and `StatusSeeder` explicitly. There is still **no `TicketFactory`** — TM-59 owns it; until then tests build tickets with a local helper, as Stories 17, 18 and 31 do.

- **Story 45 does not depend on Story 44, and neither blocks the other.** One notifies an agent and builds a deep link; the other notifies a contact record and deliberately builds none. They share no file except `docs/api-contract.md`. What Story 45 reuses is the *shape* — domain event dispatched after commit → auto-discovered listener → queued notification — repeated on purpose rather than reinvented.

- **Story 45 breaks Story 44's "no `resources/views/mail/`" rule, and the reason is measured.** TM-53's second criterion is *"echoes the subject and description **as submitted**"*, and `MailMessage->line()` cannot do that. A probe description containing `**stars**`, `# hash`, `[click me](http://evil.test)` and newlines came out with the link **live**, the markdown consumed and **every newline collapsed into one paragraph**. Through a two-view `MailMessage` the same input rendered literally, `html_len=246` / `text_len=170`, with the newline preserved inside `<pre>`. **`MailMessage->line()` is right for labelled fields (TM-52) and wrong for verbatim user text (TM-53).** TM-56 extracts a shared layout from the views TM-53, TM-54 and TM-55 create — which is only possible because they create them.

- **`{{ }}` in a mail HTML view, `{!! !!}` in the matching text view.** Measured: Blade's `{{ }}` HTML-escapes in a plain-text template too, emitting `&lt;b&gt;html&lt;/b&gt;` where the entity is simply wrong output. The text part is never parsed as markup, so unescaped is correct there; the HTML part must stay escaped — it is what turned `<script>` into `&lt;script&gt;`. **Every E8 view pair follows this split, and Story 45 ships a regression test on each half.**

- **The requester's email carries no link, and that is a product fact rather than an omission.** TM-21's first criterion is *"no login capability"*, and `POST /api/v1/tickets` sits inside the `auth:sanctum` group — **there is no public intake form and no requester portal.** A `/tickets/{id}` link would land a requester on a login page they can never pass. **The reference is the affordance**; the instruction is to quote it in a reply. A portal or magic link needs its own story.

- **AC4 of TM-53 describes a state the schema forbids, and the guard ships anyway — keyed on `blank()`, not `is_null()`.** `requesters.email` is `NOT NULL UNIQUE` and `StoreTicketRequest` requires a valid address; TM-21's plan says the column is `NOT NULL` *because* TM-53 emails them. But **`NOT NULL` does not forbid `''`**, which an importer, a seeder or a stray `firstOrCreate` can write, so `blank($requester->email)` is the check and a `Requester` created with `email: ''` is how the test reaches it. **Do not make the column nullable to make the test easier** — TM-22 matches requesters on it.

- **A requester confirmation says nothing the requester did not tell us.** Reference, subject, description — no priority (it defaults to `Medium` without them), no status (internal workflow vocabulary), no category (a staff taxonomy), no assignee, no creator, no escalation reason, no activity. **The listener enforces it by absence**: it eager-loads `requester` and nothing else, and the notification is handed four scalars rather than the `Ticket` model, so a template cannot reach what was never passed.

- **Story 45 discharges TM-47's deferred criterion, and its test says so.** [`../ticket-history-audit-trail/40-story-internal-notes-on-a-ticket-TM-47.md`](../ticket-history-audit-trail/40-story-internal-notes-on-a-ticket-TM-47.md) ships a tripwire asserting its note endpoint sends and queues nothing, and records at line 122 that *"excluding notes from a requester mailable remains E8-S3's and E8-S6's criterion"*. Story 45's test 10.6 writes a distinctive string into `ticket_activities.meta` and asserts it appears in neither mail part.

- **A labelling error in the escalation plans, found while planning Story 45.** [`../status-workflow-escalation/35-story-escalate-a-ticket-TM-41.md`](../status-workflow-escalation/35-story-escalate-a-ticket-TM-41.md) (lines **26**, **485**, **626**) and [`../status-workflow-escalation/36-story-escalated-tickets-are-visible-at-a-glance-TM-42.md`](../status-workflow-escalation/36-story-escalated-tickets-are-visible-at-a-glance-TM-42.md) (line **47**) all defer escalation email to "**TM-53**". **Escalation mail is TM-55** (E8-S5, *"Notify admins on escalation"*); TM-53 is the requester's creation confirmation. **Story 45 adds no escalation notification**, and the mislabel is recorded here so TM-55 is not skipped on the strength of a plan that says it is already spoken for.

- **Story 46 owns both the event and the dispatch point, unlike Stories 44 and 45.** Story 44 inherited `TicketAssigned` from Story 29 and Story 45 added a one-line dispatch to an implemented `store()`. **No E6 story dispatches anything** — Story 32's scope list ends *"**No notification** — E8 owns every line of mail"*, Story 34's *"no reopen notification (E8)"* — so Story 46 creates `TicketStatusChanged` and threads it out of a `changeStatus()` that Stories 32, 33 and 34 build between them. **All three are hard gates and none exists on disk**: no `changeStatus()`, no `TicketWorkflow`, no `TicketTimestamps`, no `Status::SLUG_*`, no `StatusChanged` enum case.

- **`config/notifications.php` is the project's second bespoke config file, and TM-55 and TM-57 extend it.** AC3 says the visible-status list must be *"configuration driven, not hardcoded at the call site"*, which rules out a `match ($to->slug)` in the controller. A `notify_requester` column was rejected on the rule Story 33 already set — *"which moves are legal stays data; what three statuses mean is code"*. **Keep the two-level `requester.*` shape** so TM-55's admin-recipient rule and TM-57's retry policy sit alongside without a restructure.

- **`new` and `open` are deliberately not requester-visible.** Default `NOTIFY_REQUESTER_STATUSES=in-progress,pending,resolved,closed,reopened`. `new` would email seconds after TM-53's confirmation; `open` is a triage step with no requester-facing meaning, and including it would email nearly every ticket twice in a minute — the exact burst AC5 exists to stop. **`pending` is the one nobody should ever drop: it usually means the ticket is waiting on the requester.**

- **AC5 is a delay plus supersede-at-send, not a cooldown lock — and the alternatives were ruled out on measured grounds.** The notification's `withDelay()` holds each message for the configured window and `shouldSend()` drops it when the ticket's `status_id` no longer matches the one it was queued for, so four rapid moves produce **one** email describing the final state. A `Cache::add()` cooldown was rejected because it suppresses the **later** change — it would say "in progress" and never "resolved". **Laravel 13's notification deduplicator is inert on this queue**: `NotificationSender::queueNotification()` passes it to `->withDeduplicator()`, but the only consumer in the framework is `Illuminate/Queue/SqsQueue.php:581`. **`ShouldBeUnique` is not available either** — `SendQueuedNotifications` implements `ShouldQueue` and nothing else.

- **`shouldSend()` runs in the worker, after the delay — verified.** `SendQueuedNotifications::handle()` calls `sendNow()`, which reaches `NotificationSender::shouldSendNotification()` and calls `shouldSend($notifiable, $channel)`. **`withDelay()` is the hook rather than a `$delay` property** because `queueNotification()` prefers the method, and a method reads `config()` at queue time instead of freezing the window at construction.

- **Every AC5 test must move Carbon's clock, and must count `jobs` rows before it does.** `DatabaseQueue` filters on `available_at <= currentTime()`, so a delayed job is invisible to `queue:work` until `travelTo()` advances time. **A test that forgets the travel sees an empty queue and goes green for the wrong reason** — asserting the row count first is what stops an unreached job masquerading as a suppressed one. Relatedly, **`Notification::fake()` bypasses `shouldSend()` entirely**, so suppression can only be tested end to end or by calling the method directly.

- **`$from->getKey()` is captured inside the transaction closure, and a test guards it.** `$from` is the status read after `refresh()` and before `save()`; reading it outside would make every email say `Resolved → Resolved`. Story 46 changes the closure's return to `[$ticket, $fromStatusId]` for that reason alone and changes nothing else inside it.

- **The status email quotes the resolution note and never the reopen reason.** Both live in the same `meta` bag after Story 34, but a resolution is written for the requester and a reopen reason is a note staff write to each other. The event carries only `resolution`, so the template cannot reach the other one.

- **Story 46 is the second of three view pairs TM-56 unifies.** It repeats Story 45's measured rules without re-deriving them: a Blade view pair rather than `MailMessage->line()` because a resolution note is free text whose newlines and markdown must survive, and **`{{ }}` in the HTML view with `{!! !!}` in the text view** because Blade escapes in plain-text templates too. **TM-55 creates the third; extracting the layout is TM-56's job, not theirs.**

- **Story 47 is the story Stories 35 and 36 called "TM-53".** Those plans defer escalation mail to TM-53 at four places (**35**: lines 26, 485, 626; **36**: line 47). **TM-53 is the requester's creation confirmation; escalation mail is TM-55.** Story 45 recorded the mislabel so this story would not be skipped on the strength of a plan claiming it was already owned. **Do not edit those four lines** — note the correction in the PR.

- **Like Story 46, Story 47 owns both the event and the dispatch point.** Story 35 writes two activity rows and dispatches nothing, saying only that E8 owns the mail. So Story 47 creates `TicketEscalated` and threads it out of an `escalate()` that Story 35 builds — one line between the closing `});` and the existing `return`. **Unlike Story 46 it needs no capture gymnastics**: `escalation_level` is incremented inside the closure and the closure returns the ticket, so the new level is simply there.

- **"All active admins" is taken literally, including an admin who escalated.** TM-52's self-exclusion existed because that story has an explicit criterion demanding it; **TM-55 has no such clause**, and `TicketPolicy::escalate()` is a pure role gate after Story 35, so the actor is frequently an agent and the exclusion would be a no-op anyway. Story 35 made the same call for routing — *"the actor is not excluded"*. **The tension is recorded, not hidden**: `NOTIFY_ESCALATING_ADMIN=false` flips it without a code change, and one test pins both sides.

- **The escalation subject breaks this epic's reference-first convention on purpose.** TM-52 and TM-54 lead with `[{reference}]`; TM-55 leads with `[ESCALATED` because **AC3 is about mail-client filtering**, and a filter rule matches a prefix far more reliably than a middle. The token is bracketed so a ticket subject reading "ESCALATED: help" cannot forge it — the ticket's own subject is echoed *after* the token.

- **AC4 is carried three ways, and `×1` must never render.** The `×N` subject suffix, an extra body line above level one, and an `X-Ticket-Escalation-Level` header for numeric filtering. **This follows TM-42's badge rule exactly** — its plan states twice that *"a bare 'Escalated' is the level-one signal"* and *"Never `×1`"* — so the queue badge and the inbox subject teach one convention rather than two. **An implementer writing the suffix unconditionally is the single likeliest defect in this story**, and one test exists solely to catch it.

- **Story 47 deliberately does not repeat TM-54's delay-and-supersede machinery.** Escalation is a considered act with a mandatory 10–5000 character reason, and **level 1 → level 2 is exactly the distinction AC4 requires** — suppressing the second email would delete it. It is also the "reach me when I am not looking at the board" signal, so holding it back defeats the purpose. **A reviewer reaching for supersession here has misread both stories.**

- **`Notification::send()` fans out to one job per recipient — verified, and the tests count it.** `NotificationSender::queueNotification()` loops `foreach ($notifiables as $notifiable)` and dispatches a `SendQueuedNotifications` **inside** that loop, so three active admins produce **three** `jobs` rows. A transport failure therefore loses one recipient rather than all of them, and `queue:retry` can replay just that one.

- **Story 47 creates the third and final view pair TM-56 unifies.** It repeats Story 45's measured rules — a Blade view pair rather than `MailMessage->line()`, `{{ }}` in HTML and `{!! !!}` in text — but it is the **one E8 email allowed to carry internal information**: it names staff, the assignee and the priority, and carries a deep link, because every recipient is an admin. TM-56's fifth criterion still bars internal note bodies and stack traces.

- **`AdminUserSeeder` creates exactly one admin, and only when `ADMIN_PASSWORD` is set — which `phpunit.xml` never does.** Every recipient test in Story 47 builds its own admins with `User::factory()->admin()` and `->inactive()`. Story 35's plan carries the same warning for the same reason.

- **Story 48 is a refactor with four hard gates and no new behaviour.** It ships no notification, no recipient rule, no subject line and no field decision — every one of those stays exactly as Stories 44–47 wrote it. **A layout extracted from three of the four emails is a layout extracted twice**, so the gate is all four mail suites green before task 1.

- **Its real risk is a green suite that stopped proving anything.** Stories 44–47 carry roughly 45 content assertions between them. **Record the pass count before the first edit and compare after the last**: minus two, with two amended tests, is right; minus ten is a view that quietly stopped rendering a field. Blade does not error on a child that extends a layout and defines no matching section, so a mistyped `@section('body')` renders four blank emails silently — one test exists solely to catch that.

- **Story 44's email is the one still on `MailMessage->line()`, and moving it breaks exactly two of its tests.** `MailMessage::view()` nulls the markdown message, so `$mail->actionUrl` becomes `null` — which `test_it_links_to_the_spa_ticket_page_by_numeric_id` and `test_a_trailing_slash_on_the_frontend_url_does_not_double` assert directly. **Amend both in place to assert the rendered URL; do not delete them and do not copy them into Story 48's own file.** Its handover note also gains the `<pre>` block the other three already have, fixing the newline collapse `->line()` was causing.

- **The layout carries no link, and that is forced by two existing tests.** Stories 45 and 46 both assert a requester email contains no `localhost:5173`, no `config('app.frontend_url')` and no `/tickets/` — because a requester has **no login** and there is no portal. **A footer link in the shared layout breaks both on the day it is written.** AC4's "base URL from configuration" is discharged instead by the two staff emails plus a source-scanning test asserting no mail template or notification contains an `http://` or `https://` literal.

- **A correctness fix falls out of the refactor.** The framework's default notification template links its header to `config('app.url')` — measured for Story 44, its text part opened `Ticket Management: http://localhost:8000`. **That is the API base URL, not the SPA.** No email should ever have pointed a human at port 8000, and moving TM-52 onto the project layout removes it.

- **The summary partial owns presentation and never content policy.** It takes a `label => value` map the **notification** builds, because TM-53's and TM-54's requester emails deliberately omit priority, status and category and both have tests asserting it. **A partial that decided for itself what a ticket summary contains would break four tests and one acceptance criterion on the day it was written.** Free text — description, resolution note, escalation reason — is never a row; it keeps its own `<pre>` block.

- **Blade layout inheritance works in a text template, measured.** A layout + child rendered through `MailMessage->view([...])` gave `html_len=1532`, `text_len=138`, and this exact text part: `"Ticket Management\n\nHello Dana,\n\nReference: TKT-2026-000042\nSubject: Printer offline\n\nline one\nline two **not bold**\n\n-- Ticket Management\n"`. **The blank lines are load-bearing and the partial's `@foreach` must sit flush left** — that is what yields one clean `Label: value` line per row.

- **"Degrades gracefully without CSS" is a test, not a claim.** One test strips the `<style>` block and every `style` attribute and asserts every label, value, note and URL survived; another asserts no template hides content with `display:none`, `visibility:hidden`, `font-size:0`, `background-image` or `mso-hide`. **Desktop appearance lives in inline attributes and only the mobile improvement lives in the `<style>` block**, because Gmail strips the block in some contexts — so losing it degrades to a fixed 600px card rather than to unstyled text.

- **`MailLayoutTest` is where every future email inherits AC2–AC5.** It renders all four notifications from one deliberately hostile fixture — a soft-deleted category, a staff address, an internal-note canary in `ticket_activities.meta` — and runs every assertion four times. **A notification absent from its array is a notification nobody is checking**, and the file says so.

- **No mail template may use Tailwind, `@vite()`, a web font or an image.** `backend/package.json` carries Tailwind 4 and Vite 8 for **Blade-side browser assets**; a mail client runs no build step and fetches no stylesheet.

- **Story 49 is the epic's closing bill, and every earlier story wrote a line on it.** Stories 44–47 each deferred `tries`, `backoff`, `timeout`, `retryUntil` and `ShouldQueueAfterCommit`; Story 43 deferred `config/queue.php:44`'s `after_commit` and recorded `retry_after = 90` with *"no job declares a timeout yet"*; Story 48 restated that TM-57 owns the retry policy. **It ships no new email, recipient, event, listener or template** — only a policy, a failure log, and one suite that enforces four rules across all four events.

- **`after_commit` stays `false`, and the reason was traced through the framework rather than assumed.** Turning it on would defer every job into `DatabaseTransactionsManager::addCallback()`, which attaches to `callbackApplicableTransactions()->last()` — plainly `$this->pendingTransactions`, **with no test-connection exemption in this version**. `RefreshDatabase::beginDatabaseTransaction()` installs a fresh manager and then begins a transaction, registering it as pending. **So under `RefreshDatabase` the job attaches to a transaction that is rolled back and is never pushed** — silently zeroing roughly a dozen `DB::table('jobs')->count()` assertions across Stories 44–47, plus Story 46's `available_at` checks and Story 47's three-jobs-per-admin count. **AC4 is already true structurally** — all four events dispatch after `DB::transaction()` returns — so the flag would buy a net for a mistake nobody has made. A test pins it to `false`, and a verification step asks the executor to flip it once and watch the suite fall over.

- **Three retry settings, three different framework mechanisms, and two of them fail silently if you guess.** `tries` and `timeout` are read from a **property** by `SendQueuedNotifications::__construct()` via `getAttributeValue()` — **a `tries()` method is never called**. `backoff` is read from a **method**: `SendQueuedNotifications::backoff()` overrides the attribute with `$notification->backoff()` when it exists. `failed($e)` is a **method** that `SendQueuedNotifications::failed()` forwards to, and it is the only hook AC2's *"with context"* can use. **`App\Notifications\Concerns\HasRetryPolicy` encodes all three**, and the tests assert the values reach `jobs.payload` — the only proof the framework actually read them.

- **An array backoff becomes a comma string in the payload.** `Queue::getJobBackoff()` does `Collection::wrap($backoff)->implode(',')` and `Worker::calculateBackoff()` does `explode(',', $job->backoff())`, indexing by attempt and **repeating the last entry**. So `[60, 300]` with `tries = 3` gives 60s then 300s, and raising `NOTIFY_TRIES` to 5 without adding entries gives 60, 300, 300, 300 — intended, and recorded before someone "fixes" it.

- **`timeout` must stay below `retry_after`, and a one-line test makes that a red suite instead of a footgun.** `config/queue.php:43` sets `retry_after` to 90; the policy sets `timeout` to 30. A job allowed to run longer than `retry_after` is handed to a second worker while the first is still sending it. **`timeout` also needs `ext-pcntl`** — without it the value is inert, which is why the plan asks the executor to record `php -m | grep -c pcntl` in the PR.

- **The failure hook logs and does nothing else.** `failed_jobs` already holds the payload and the full exception; the `Log::error` holds what that row cannot give you without unserialising it — ticket id, reference, notification class. **No email is sent about a failed email**, no automatic re-queue (Story 43 documented `queue:retry` for this moment), and **`failureContext()` returns scalars and never an address** — TM-56's fifth criterion applied to the log file. It also must not query the database, or a connection failure becomes a second exception inside the failure handler.

- **AC4 gets an architectural test, not a config flag.** A temporary listener records `DB::transactionLevel()` at dispatch time and the test asserts it equals a baseline captured in the test body — proving the controller's own transaction had closed. **Asserting `=== 0` would be wrong**: `RefreshDatabase` holds a transaction open for the whole test, so zero is unreachable and the assertion would fail for a reason that teaches the next reader something untrue.

- **A mail outage is simulated with a host `MailSafety` permits on a port nothing listens to.** `127.0.0.1:1` is in the guard's `safe_smtp_hosts`, so the transport is allowed to be built and then fails to connect — which is exactly the shape of a real relay outage, without touching Story 43's guard or opening a socket to anything real.
